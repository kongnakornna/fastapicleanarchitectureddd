ส่วนที่ 12: ตัวอย่างจริงและภาคผนวก (บทที่ 111–120)


บทที่ 111: ตัวอย่าง Data Workflow


1. เรื่อง

ตัวอย่างแผนภาพและสถาปัตยกรรมทางเดินข้อมูล (Data Workflow) ของระบบฐานข้อมูล GridCare ในระดับ Enterprise Production

2. วัตถุประสงค์

เพื่อให้วิศวกรระบบเห็นโครงสร้างการไหลของข้อมูลตั้งแต่จุดเริ่มต้น (Data Source) ผ่านตัวกรอง ไปจนถึงการเก็บรักษาและนำไปใช้งานจริงอย่างเป็นระบบ

3. เป้าหมาย

ผู้อ่านสามารถอธิบายโครงสร้าง Data Pipeline ของ PostgreSQL และระบุหน้าที่ของ Layer ต่าง ๆ รวมถึงความเกี่ยวเนื่องกับไฟล์คอนฟิกระบบได้

4. เนื้อหาโดยย่อ

โครงสร้าง Data Workflow บน Production ที่ดีต้องมีการแยกแยะหน้าที่อย่างชัดเจน (Separation of Concerns) ข้อมูลแอปพลิเคชัน (Application Data) จะวิ่งผ่านชั้น Connection Pooler และ Load Balancer เข้าสู่ฐานข้อมูลหลัก จากนั้นจะถูกแตกแขนงออกเป็น 2 ทางหลัก คือ ข้อมูลธุรกรรมเพื่อสตรีมมิ่งไปยังโหนดสำรอง (Replication Flow) และข้อมูลความปลอดภัย/การสำรองข้อมูล (Backup/WAL Archive Flow) วิ่งออกสู่ Object Storage เพื่อความปลอดภัยสูงสุด

5. ประโยชน์ที่ได้รับ

• เข้าใจจุดเสี่ยงคอขวดและจุดที่มีโอกาสพัง (Single Point of Failure: SPOF) ในระบบทางเดินข้อมูล
• สามารถวางแนวป้องกันข้อมูลรั่วไหลในแต่ละเลเยอร์ได้ตามมาตรฐาน PDPA
• ช่วยให้ทีม Infra ออกแบบระบบเครือข่าย (Network Zoning) และ Firewall Rules ได้อย่างถูกต้อง

6. ข้อควรระวัง

การขาดระบบตรวจสอบสถานะของทางเดินข้อมูลย่อย (เช่น ลืมมอนิเตอร์สถานะการส่ง WAL File) อาจทำให้ระบบล่มแบบโดมิโนเมื่อพื้นที่ดิสก์เต็ม

7. ข้อดี

• ข้อมูลมีความเป็นระบบสูง กู้คืนได้ง่าย และขยายสเกลโหนดอ่าน (Read Replica) ได้อย่างรวดเร็ว
• สอดคล้องกับมาตรฐานความปลอดภัยระดับสากล

8. ข้อเสีย

• มีจำนวนองค์ประกอบ (Components) หลายชิ้นในระบบ ทำให้ต้องใช้เครื่องมืออัตโนมัติในการควบคุมดูแล

9. ข้อห้าม

ห้ามปล่อยให้ทางเดินข้อมูลการสำรองข้อมูล (Backup Path) วิ่งผ่านระบบเครือข่ายหลักของแอปพลิเคชันโดยไม่มีการจำกัดปริมาณ Bandwidth (Throttling) ในช่วงเวลาเร่งด่วน

10. รายละเอียด

แผนผังโครงสร้าง Data Workflow สถาปัตยกรรม Enterprise:
text
[ชั้นแอปพลิเคชัน / ลูกข่าย]
         │
         ▼
[PgBouncer :6432]  ◄── (บริหารจัดการ Connection Pool ลด Overhead)
         │
         ▼
[HAProxy :5000 / :5001] ◄── (สแกนตรวจสุขภาพแยกโหนดเขียนโหนดอ่านผ่านพอร์ต 8008 ของ Patroni)
         │
 ┌───────┴────────────────────────────┐
 │ (ทางเดินข้อมูลหลัก: โหนดเขียน)      │ (ทางเดินข้อมูลรอง: โหนดอ่าน)
 ▼                                    ▼
[pg1: Primary PostgreSQL 18]        [pg2: Replica PostgreSQL 18]
 │       │                                    ▲
 │       └──────(Replication Flow: Wal Slots)─┘  *(ทำ pg_rewind อัตโนมัติหากโหนดหลักพัง)
 │

         │

11. ตัวอย่าง

ตัวอย่างการยืนยันสถานะ Data Workflow ของ WAL Archive ว่าวิ่งเข้า Object Storage (MinIO) บนโหนด Primary อย่างถูกต้อง:
bash

12. สรุปย่อ

Data Workflow คือพิมพ์เขียวชีวิตของข้อมูล การออกแบบเส้นทางการวิ่งของข้อมูลให้มีเลเยอร์ป้องกันและระบบสลับโหนดอัตโนมัติ คือพื้นฐานสำคัญของการทำระบบฐานข้อมูล Enterprise High Availability

บทที่ 112: ตัวอย่าง Metric Workflow


1. เรื่อง

ตัวอย่างพิมพ์เขียวการไหลของสถิติและตัวชี้วัดระบบ (Metric Workflow) ผ่าน Prometheus Exporters เข้าสู่หน่วยจัดเก็บข้อมูลอนุกรมเวลา

2. วัตถุประสงค์

เพื่อแสดงโครงสร้างการรวบรวมข้อมูลสถานภาพ (Observability Data) จากฐานข้อมูลและระบบปฏิบัติการลินุกซ์ แปลงสภาพ และส่งต่อให้ระบบแสดงผลอย่างมีประสิทธิภาพ

3. เป้าหมาย

ผู้อ่านสามารถบอกทิศทางและกลไกการทำงานของระบบ Metric Collection แบบ Pull-based Model และระบุพอร์ตมาตรฐานของเครื่องมือมอนิเตอร์ได้

4. เนื้อหาโดยย่อ

Metric Workflow บน Production จะไม่ใช้การดึงข้อมูลจากตัว Engine ฐานข้อมูลโดยตรงเพื่อป้องกันผลกระทบด้านความเร็ว แต่จะพึ่งพาหน่วยย่อยที่เรียกว่า Exporters ทำหน้าที่แปลงสถานะภายในให้เป็นโครงสร้างข้อความรูปแบบ OpenMetrics จากนั้นเซิร์ฟเวอร์มอนิเตอร์ส่วนกลาง (Prometheus) จะทำหน้าที่กวาดข้อมูล (Scrape) ตามรอบเวลาจัดเก็บเข้าสู่ Time-Series Database (TSDB) เพื่อพร้อมรับคำสั่งสืบค้นจากแดชบอร์ด

5. ประโยชน์ที่ได้รับ

• แยกแยะภาระงานการมอนิเตอร์ออกจากระบบประมวลผลธุรกรรมหลักอย่างชัดเจน
• สามารถเก็บข้อมูลประวัติย้อนหลังเพื่อทำสถิติทำนายอนาคต (Capacity Planning) ได้
• รองรับสถาปัตยกรรมแบบกระจายศูนย์ (Multi-node Monitoring)

6. ข้อควรระวัง

การตั้งค่ารอบเวลาการดึงข้อมูล (Scrape Interval) ถี่เกินไป (เช่น ทุก 1 วินาที) จะสร้างภาระให้ CPU และระบบ I/O ของฐานข้อมูลโดยไม่จำเป็น ค่าที่แนะนำสำหรับ Production คือ 15-30 วินาที

7. ข้อดี

• สถาปัตยกรรมแบบ Pull Model ป้องกันปัญหาระบบมอนิเตอร์พังแล้วส่งผลกระทบย้อนกลับไปทำให้ฐานข้อมูลหลักล่ม (Cascading Failure)
• มาตรฐานสากล ใช้ร่วมกับแดชบอร์ดและทูลมอนิเตอร์ระดับโลกได้ทุกประเภท

8. ข้อเสีย

• ข้อมูลมีความละเอียดระดับวินาทีตามรอบที่ตั้งไว้ ไม่เหมาะสำหรับงานประเภท Real-time Audit ระดับมิลลิวินาที (ซึ่งงานประเภทนั้นควรไปพึ่งพา pgAudit Log)

9. ข้อห้าม

ห้ามเปิดพอร์ต Exporter (:9100, :9187, :8008) ออกสู่เครือข่ายสาธารณะภายนอกโดยไม่มีการจำกัดสิทธิ์ IP (Firewall) หรือไม่มีการเข้ารหัสผ่าน

10. รายละเอียด

พิมพ์เขียวสถาปัตยกรรม Metric Workflow:
text
[ โหนดเซิร์ฟเวอร์ฐานข้อมูล: pg1 / pg2 ]
 │
 ├──► [node_exporter :9100] ───────► แปลง Metric ของ OS (CPU, RAM, Disk, Network)
 ├──► [postgres_exporter :9187] ───► แปลง Metric ของ Engine (TPS, Locks, Cache Hit, Bloat)
 └──► [Patroni REST API :8008] ─────► แปลง Metric ของ HA Cluster (Primary/Replica Status)
                                                 ▲
                                                 │ (Scrape HTTP Pull ทุก 15 วินาที)
                                                 │
                                       [ เครื่องมอนิเตอร์ส่วนกลาง: infra ]
                                                 │
                                                 ▼
                                        [Prometheus Server :9090]
                                                 │
                                                 ├──► จัดเก็บลงหน่วยความจำอนุกรมเวลา (TSDB)
                                                 │
                                                 ▼
                                        [Grafana Dashboard :13000] ◄── (สืบค้นผ่านคำสั่ง PromQL)
ใช้โค้ดอย่างระมัดระวัง

11. ตัวอย่าง

ตัวอย่างการดึงข้อมูล Metric สถานะดิสก์ผ่านคำสั่ง curl ต้นทาง เพื่อตรวจสอบหน้าตาของข้อมูลดิบก่อนส่งเข้า Prometheus:
bash
curl -s localhost:9100/metrics | grep "node_filesystem_free_bytes{mountpoint=\"/\"}"
ใช้โค้ดอย่างระมัดระวัง
ผลลัพธ์จริงที่คาดหวัง:

ใช้โค้ดอย่างระมัดระวัง

12. สรุปย่อ

Metric Workflow คือดวงตาของวิศวกรระบบ การวางระบบเก็บสถิติที่มี Exporter ทำงานเป็นอิสระและ Prometheus เป็นผู้รวบรวมข้อมูลส่วนกลาง จะช่วยให้องค์กรมีข้อมูลดิบที่มีคุณภาพสูงในการพยากรณ์และป้องกันวิกฤตการณ์ก่อนเกิดเหตุจริง

บทที่ 113: ตัวอย่าง Alert Workflow


1. เรื่อง

ตัวอย่างโครงสร้างทางเดินและการบริหารจัดการสัญญาณเตือนภัย (Alert Workflow) เมื่อเกิดเหตุอุบัติการณ์บน Production

2. วัตถุประสงค์

เพื่อกำหนดขั้นตอนการตัดสินใจของระบบแจ้งเตือน ตั้งแต่จุดตรวจพบตัวเลขวิกฤต การจัดกลุ่มกรองสัญญาณ Noise ไปจนถึงการส่งต่อถึงวิศวกร On-call และ Runbook

3. เป้าหมาย

ผู้อ่านสามารถออกแบบวงจรการทำงานของระบบ Alert และเขียนโครงสร้าง Routing Tree บน Alertmanager ได้อย่างมีประสิทธิภาพ

4. เนื้อหาโดยย่อ

Alert Workflow คือการเปลี่ยนผ่านจากข้อมูล Metric ที่มีค่าผิดปกติให้กลายเป็นภารกิจการกู้ภัย (Actionable Task) เมื่อ Prometheus ประเมินผลคำสั่ง PromQL แล้วพบว่าเกินเกณฑ์ที่กฎกำหนด ระบบจะเข้าสู่สถานะรอการยืนยัน (Pending) เมื่อครบเวลาหน่วง (for:) ระบบจะยกระดับเป็นสัญญาณระเบิด (Firing) แล้วส่งไม้ต่อให้ Alertmanager ทำหน้าที่รวบรวม กรองตัวซ้ำ (Deduplication) และเลือกเส้นทางจัดส่งเข้าช่องทางการสื่อสารที่เหมาะสมตามระดับความรุนแรง

5. ประโยชน์ที่ได้รับ

• สยบปัญหา Alert Fatigue ทีมงานจะไม่ถูกปลุกจากข้อความแจ้งเตือนที่ไม่ได้ระบุปัญหาวิกฤตจริง
• วิศวกร On-call มี Runbook เปิดอ่านทำตามขั้นตอนแก้ปัญหาได้ทันทีภายใน 5 นาทีแรก
• มีระบบบันทึกสถานะการแจ้งเตือนและการกู้คืน (Resolved) โดยอัตโนมัติ

6. ข้อควรระวัง

การตั้งค่าเวลาจัดกลุ่มสัญญาณเตือน (group_wait) ยาวเกินไป อาจทำให้ทีมงานรับทราบเหตุการณ์วิกฤตช้าลง ในขณะที่การตั้งสั้นเกินไปจะทำให้เกิดข้อความแจ้งเตือนกระจายตัวถล่มช่องแชต

7. ข้อดี

• กรองและจัดกลุ่ม Alert ที่เกิดจากต้นตอเดียวกัน (เช่น ดิสก์พังโหนดเดียว แต่มี Alert ดังพร้อมกัน 5 กฎ) ให้เหลือข้อความสรุปฉบับเดียวได้
• สามารถแยกแยะช่องทางรับเรื่องตามระดับความรุนแรง (Severity) ได้

8. ข้อเสีย

• ต้องมีการอัปเดตไฟล์คอนฟิกสม่ำเสมอเมื่อมีการเปลี่ยนโครงสร้างทีม On-call หรือเปลี่ยนช่องทางสื่อสาร

9. ข้อห้าม

ห้ามปล่อยให้ Alert ระดับ Critical ส่งเข้าอีเมลส่วนตัวโดยไม่มีระบบส่งข้อความด่วน (เช่น SMS, PagerDuty หรือ Slack Alert พร้อมเสียงเตือนวิกฤต) รองรับ

10. รายละเอียด

พิมพ์เขียวเส้นทางวิ่งของสัญญาณ Alert Workflow:
text
[ Prometheus Engine ] ◄── (ประเมินคำสั่ง PromQL Alert Rules ทุก 15 วินาที)
         │
         ▼
  [ สถานะ: PENDING ]   ◄── (ตัวเลขเกินเกณฑ์ เช่น CPU > 90% แต่ยังไม่ครบเวลาหน่วง)
         │
         ▼ (เมื่อเวลาค้างนานเกินกฎ เช่น for: 5m)
  [ สถานะ: FIRING ]
         │
         ▼ (จัดส่งในรูปแบบ JSON Payload)
[ Alertmanager :9093 ]

                   │

                                                            ▼
                                                [ เปิดลิงก์ Runbook URL ]
                                                            │
                                                            ▼
                                                [ ดำเนินการแก้ไขระบบ ]

1. เรื่อง

แม่แบบคู่มือปฏิบัติการแก้ไขปัญหาด่วน (Operational Runbook Template) สำหรับงานวิศวกรรมฐานข้อมูลระบบ Production

2. วัตถุประสงค์

เพื่อให้วิศวกร On-call มีขั้นตอนปฏิบัติงานกู้ภัยระบบที่เป็นมาตรฐาน ชัดเจน แม่นยำ และสามารถทำตามได้ทันทีภายใต้สภาวะกดดันสูง

3. เป้าหมาย

ผู้อ่านสามารถนำแม่แบบนี้ไปสร้างคู่มือ Runbook ประจำองค์กร โดยระบุคำสั่งตรวจสอบ วิธีแก้ไข และการ Rollback ได้อย่างสมบูรณ์

4. เนื้อหาโดยย่อ

Runbook คือเอกสารที่ต้องถูกเข้าถึงได้ง่ายผ่านลิงก์ URL ที่แนบมากับข้อความ Alert เนื้อหาภายในจะไม่เน้นการเขียนอธิบายทฤษฎียาวๆ แต่จะเน้นการให้ คำสั่งสแกนหารอยโรค (Diagnosis) และ คำสั่งกู้ระบบ (Resolution) แบบ Copy-Paste ได้ทันที พร้อมระบุขั้นตอนการตรวจสอบยืนยันผลลัพธ์ว่าระบบกลับมาเป็นปกติจริง

5. ประโยชน์ที่ได้รับ

• ลดค่าเวลากู้คืนระบบ (MTTR) ลงอย่างมหาศาลเนื่องจากไม่ต้องเสียเวลาคิดคำสั่งใหม่
• ป้องกันความผิดพลาดของมนุษย์ (Human Error) จากการพิมพ์คำสั่งผิดพลาดในสภาวะตื่นตระหนก
• ช่วยให้วิศวกรระดับ Junior หรือทีม DevOps ทั่วไปสามารถแก้ไขปัญหาระดับสูงแทน DBA ได้ชั่วคราว

6. ข้อควรระวัง

Runbook ที่ไม่ได้ถูกอัปเดตเกิน 6 เดือนหรือมีคำสั่งที่ล้าสมัย (เช่น คำสั่งอ้างอิงพอร์ตฐานข้อมูลเก่า) อาจสร้างความเสียหายเพิ่มเติมเมื่อนำไปรันจริง

7. ข้อดี

• สร้างมาตรฐานความรู้ที่เป็นเอกภาพของทั้งแผนก
• เป็นเครื่องมือหลักในการซ้อมแผน Game Day

8. ข้อเสีย

9. ข้อห้าม

ห้ามเขียน Runbook ในลักษณะคลุมเครือ เช่น "ตรวจสอบความเหมาะสมของหน่วยความจำแล้วดำเนินการแก้ไขตามสมควร" ทุกขั้นตอนต้องระบุตัวเลขเกณฑ์และคำสั่งที่ชัดเจน

## 🔍 1. ขั้นตอนการตรวจสอบและวินิจฉัย (Diagnosis Steps)
เมื่อ Alert แจ้งเตือนเรื่องธุรกรรมค้างหรือเกิด Lock Timeout ให้เข้าเครื่อง `pg1` แล้วรันคำสั่ง psql ด้านล่างนี้ทันทีเพื่อหาหัวคิวล็อก (Root Blocker):

```sql
SELECT 
    pid, 
    usename, 
    clock_timestamp() - xact_start AS xact_age, 
    pg_blocking_pids(pid) AS blocked_by, 
    wait_event_type, 
    wait_event, 
    left(query, 100) AS short_query
FROM pg_stat_activity 
WHERE state <> 'idle' AND pg_blocking_pids(pid) <> '{}' OR pid IN (SELECT unnest(pg_blocking_pids(pid)) FROM pg_stat_activity)
ORDER BY xact_age DESC;
```

**เกณฑ์การตัดสินใจ (Decision Criteria):**
*   หากพบ Session ที่มี `xact_age` เกิน 5 นาที และค่า `blocked_by` เป็นช่องว่าง `{} ` แสดงว่าตารางนั้นคือ **หัวคิวล็อก (Root Blocker PID)** ที่ทำให้แถวอื่นพังทลาย
*   ตรวจสอบคอลัมน์ `short_query` เพื่อดูว่าระบบเป็นคำสั่ง DDL ที่รันผิดเวลา หรือคำสั่ง DML ค้างจากแอปพลิเคชัน

---

## 🛠️ 2. ขั้นตอนการแก้ไขปัญหา (Resolution Steps)
หลังระบุหมายเลข `pid` ของหัวคิวล็อกได้แล้ว ให้ดำเนินการตามลำดับขั้นความปลอดภัยดังนี้:

### ขั้นที่ 2.1: ส่งสัญญาณยุติคำสั่งแบบนุ่มนวล (Cancel Query)
คำสั่งนี้จะตัดเฉพาะงานที่รันอยู่แต่รักษาการเชื่อมต่อของแอปพลิเคชันไว้:
```sql
SELECT pg_cancel_backend(<ROOT_BLOCKER_PID>);
```
*รอเวลา 10 วินาที หาก Session หัวคิวยังไม่ยอมออก ให้ยกระดับขั้นถัดไป*

### ขั้นที่ 2.2: สั่งตัดการเชื่อมต่อขั้นเด็ดขาด (Terminate Session)
คำสั่งนี้จะฆ่ากระบวนการเชื่อมต่อทิ้งทันที:
```sql
SELECT pg_terminate_backend(<ROOT_BLOCKER_PID>);
```

---

## ✅ 3. ขั้นตอนการตรวจสอบยืนยันหลังกู้ระบบ (Verification Steps)
รันคำสั่งตรวจนับจำนวนคิวล็อกค้างเพื่อตรวจสอบว่าตัวเลขกลับสู่สภาวะปกติจริง:
```sql
SELECT count(*) FROM pg_stat_activity WHERE pg_blocking_pids(pid) <> '{}';
```
*ผลลัพธ์ที่ยอมรับได้: ตัวเลขต้องเป็น `0` หรือลดลงต่ำกว่าเกณฑ์วิกฤตทันที และกราฟ TPS บน Grafana ต้องเด้งกลับมาขึ้นระดับปกติ*

---

## 🔙 4. แผนงานการคืนสภาพระบบกรณีฉุกเฉิน (Rollback Plan)
หากการทำ Terminate Session ส่งผลกระทบทำให้แอปพลิเคชันฝั่งลูกข่ายหลุดการเชื่อมต่อเป็นวงกว้าง ให้ดำเนินการสั่งรีสตาร์ตหน่วยจัดการ Connection Pool ส่วนกลางทันที:
```bash
sudo systemctl restart pgbouncer
```
ใช้โค้ดอย่างระมัดระวัง

บทที่ 115: Template Incident Record


1. เรื่อง

แม่แบบฟอร์มบันทึกข้อมูลอุบัติการณ์ (Incident Record Template) สำหรับการเคลียร์ปัญหาและทำสรุปหลังระบบขัดข้อง

2. วัตถุประสงค์

เพื่อให้ทีมงานปฏิบัติการมีโครงสร้างเอกสารที่เป็นสากลในการจดบันทึกไทม์ไลน์ อาการ และข้อมูลทางเทคนิคของเหตุการณ์ล่ม สำหรับใช้เป็นสารตั้งต้นในการประชุมทำ RCA และ PSR ต่อไป

3. เป้าหมาย

ผู้อ่านสามารถนำแม่แบบนี้ไปกรอกข้อมูลสรุปเหตุการณ์จริงได้อย่างครบถ้วน มีสถิติตัวเลขที่ชัดเจน และพร้อมเผยแพร่ให้ผู้เกี่ยวข้องรับทราบได้ภายใน 24 ชั่วโมงหลังจบเหตุการณ์

4. เนื้อหาโดยย่อ

ฟอร์ม Incident Record คือเอกสารสรุปหน้าเดียว (One-page Dashboard Summary) ที่บันทึกข้อเท็จจริงทางประวัติศาสตร์ของระบบขัดข้อง เนื้อหาภายในประกอบด้วยรหัสตั๋วปัญหา ระดับความรุนแรง ระยะเวลา Downtime สถิติ RTO/RPO เชิงตัวเลขจริง และบทสรุปการแก้ไขเบื้องต้น เพื่อป้องกันปัญหาการลืมข้อมูลดิบเมื่อเวลาผ่านไป

5. ประโยชน์ที่ได้รับ

• รวบรวมหลักฐานทางเทคนิคทั้งหมด (Log, Metric, Code Version) ให้อยู่ในที่เดียวกันอย่างเป็นระเบียบ
• คำนวณค่า RTO และ RPO ที่เกิดขึ้นจริงเพื่อนำไปเปรียบเทียบกับเป้าหมายตามสัญญา SLA ของบริษัท
• ลดเวลาในการอธิบายข้อมูลซ้ำให้แก่ทีมบริหารและผู้ตรวจสอบภายนอก (Auditors)

6. ข้อควรระวัง

ห้ามกรอกข้อมูลในลักษณะคาดเดาความรู้สึกเอง ทุกอย่างที่ลงในบันทึกต้องมีหลักฐานระบุเวลา (Timestamp) ยืนยันจากระบบส่วนกลาง

7. ข้อดี

• กะทัดรัด สื่อสารง่าย อ่านจบได้ภายใน 3 นาที
• เป็นสารตั้งต้นที่สมบูรณ์แบบสำหรับการทำ Blameless Postmortem ในระดับถัดไป

8. ข้อเสีย

• ต้องมีวิศวกร On-call หรือผู้จัดการอุบัติการณ์ (Incident Manager) คอยทำหน้าที่จดบันทึกเวลาระหว่างเกิดเหตุการณ์จริง

9. ข้อห้าม

ห้ามลงข้อมูลสรุปงานแก้ปัญหาโดยไม่มีขั้นตอนการยืนยันผล (Validation Method) กำกับท้ายเอกสาร

11. ตัวอย่างและคำอธิบายเฉลย (Answer Keys & Detailed Explanations)


🎯 เฉลยคำถามข้อที่ 1:

• คำตอบที่ถูกต้อง: (ข) มี Long-running Transaction หรือ Session ค้างอยู่ในสถานะ idle in transaction เปิดคาไว้ในระบบ
• คำอธิบายเหตุผล: ตามหลักการกลไกสถาปัตยกรรม MVCC (Multi-Version Concurrency Control) ของ PostgreSQL การทำลาย Dead Tuples จะเกิดขึ้นได้ก็ต่อเมื่อเศษซากข้อมูลเหล่านั้นมีค่า XID (Transaction ID) ที่เก่ากว่าธุรกรรมที่เก่าที่สุดที่ยังทำงานอยู่ (Oldest xmin) หากมีแอปพลิเคชันตัวใดตัวหนึ่งเปิดคำสั่ง BEGIN ค้างไว้แล้วไม่สั่ง COMMIT หรือ ROLLBACK (กลายเป็น idle in transaction) Engine ของ PostgreSQL จะต้องคงสภาพเศษซากข้อมูลเหล่านั้นไว้เพราะคิดว่าธุรกรรมเก่าตัวนั้นอาจจะหันกลับมาเรียกสืบค้นข้อมูล ทำให้กระบวนการ Autovacuum ทำได้เพียงสแกนผ่านแต่ไม่สามารถลบแถวทิ้งได้ ส่งผลให้ตารางบวมในที่สุด

🎯 เฉลยคำถามข้อที่ 2:

• คำตอบคำนวณ: ค่า shared_buffers ที่เหมาะสมตามสูตรระดับ Enterprise (25% ของแรมทั้งหมด) คือ 16 GB (คำนวณจาก 64 GB × 0.25)
• คำอธิบายเหตุผล: เหตุผลที่ไม่ควรตั้งค่า shared_buffers สูงเกินไปหรือเกิน 50% ของแรมทั้งหมด เนื่องจาก PostgreSQL ไม่ได้ทำหน้าที่จัดการระบบ I/O และเขียนข้อมูลลงดิสก์ด้วยตัวเองโดยตรง แต่ทำงานควบคู่และพึ่งพาระบบจัดการแคชของระบบปฏิบัติการลินุกซ์ที่เรียกว่า Page Cache (OS Cache) หากเรายกหน่วยความจำให้ shared_buffers มากเกินไป จะทำให้เกิดสภาวะแคชซ้ำซ้อน (Double Buffering) และเหลือหน่วยความจำแรมไม่เพียงพอให้ลินุกซ์ทำ Page Cache ซึ่งส่งผลทำให้กระบวนการประมวลผลคำสั่งเรียงลำดับขนาดใหญ่ (Sort/Hash Operations) ที่ต้องพึ่งพา work_mem เกิดสภาวะหน่วยความจำไม่พอและต้องสปีดข้อมูลลงดิสก์ชั่วคราว ทำความเร็วตกวูบทันที

sudo -u postgres pgbackrest --stanza=gridcare --delta --type=time --target="$TARGET" --target-action=promote restore
	4. ขั้นตอนที่ 4: สั่งสตาร์ตระบบฐานข้อมูลขึ้นมาเพื่อให้ Engine ทำการอ่านไฟล์ WAL Archive จากคลังสำรองย้อนหลังไล่เวลาขึ้นมาจนกระทั่ง Recovery หยุดทำงานอัตโนมัติที่จุดวินาทีก่อน Commit ธุรกรรมที่ผิดพลาด
	5. ขั้นตอนที่ 5: ทำการสืบค้นข้อมูลในฐานข้อมูลเพื่อยืนยันว่าข้อมูลกลับมาสมบูรณ์ปกติ (ตรวจสอบว่า pg_is_in_recovery() ได้ผลลัพธ์เป็น f) จากนั้น ต้องสั่งทำ Full Backup ชุดใหม่ทันที เนื่องจากระบบได้เปลี่ยนเข้าสู่เส้นเวลาใหม่ (Timeline ID ใหม่) เป็นที่เรียบร้อยแล้ว

12. สรุปย่อ

แบบฝึกหัดบทที่ 5-8 คือการจำลองสมรภูมิจริง การแม่นยำในสูตรคำนวณและลำดับขั้นตอนการทำ PITR คือเกราะกำบังที่จะช่วยคุ้มครองฐานข้อมูล Enterprise ให้รอดพ้นจากภัยพิบัติข้อมูลสูญหายได้อย่างมั่นคง

เพื่อเป็นแผ่นข้อมูลอ้างอิงด่วนที่รวบรวมคำสั่งยอดฮิตที่ DBA และ DevOps ต้องเรียกใช้งานบ่อยในการตรวจสอบระบบประจำวัน

ผู้อ่านสามารถเรียกใช้คำสั่งตรวจสอบ Lock, ขนาดตาราง, บลอต และสถานะการทำงานภายในฐานข้อมูลได้อย่างรวดเร็วผ่านการ Copy-Paste

4. เนื้อหาโดยย่อ

คัมภีร์ Cheatsheet ฉบับนี้คัดสรรเฉพาะสูตรคำสั่ง SQL ขั้นสูงที่มีการปรับแต่งโครงสร้างการแสดงผลให้อ่านง่าย กระชับ และไม่กินทรัพยากรเครื่องระบบ Production ครอบคลุมการบริหารจัดการพื้นที่ สถิติ และการเคลียร์ปัญหาวิกฤต

📊 1. การตรวจสอบขนาดและสุขอนามัยของตาราง (Storage & Sizes)

sql
-- ค้นหาตารางที่มีขนาดใหญ่ที่สุด 5 อันดับแรกในฐานข้อมูลปัจจุบัน พร้อมขนาดดัชนี
SELECT 
    relname AS table_name,
    pg_size_pretty(pg_table_size(oid)) AS table_size,
    pg_size_pretty(pg_indexes_size(oid)) AS index_size,
    pg_size_pretty(pg_total_relation_size(oid)) AS total_size
FROM pg_class
WHERE relkind = 'r' AND relnamespace = (SELECT oid FROM pg_namespace WHERE nspname = 'gridcare')
ORDER BY pg_total_relation_size(oid) DESC LIMIT 5;
ใช้โค้ดอย่างระมัดระวัง

🔍 2. การตรวจสอบสถานะและกิจกรรมภายใน Session (Activity & Query Monitoring)

sql
-- ค้นหา 5 อันดับคำสั่งที่กำลังทำงานและใช้เวลาประมวลผลนานที่สุดในปัจจุบัน (ไม่รวม Session ที่รอสาย)
SELECT 
    pid, usename, application_name, client_addr,
    clock_timestamp() - query_start AS duration, query
FROM pg_stat_activity
WHERE state <> 'idle' AND pid <> pg_backend_pid()
ORDER BY duration DESC LIMIT 5;
ใช้โค้ดอย่างระมัดระวัง

🔒 3. การตรวจสอบปัญหาการติดล็อกและระบุหัวคิวล็อก (Lock Troubleshooting)

คุณสามารถใช้คำสั่ง SQL สำหรับค้นหา Session ที่เป็นต้นตอทำลายระบบล็อก (Root Blocker PID) และจำนวนแถวที่ติดคิวรออยู่ได้จากเอกสารอ้างอิงของ PostgreSQL ซึ่งช่วยให้ระบุความขัดแย้งของทรานแซกชันได้อย่างรวดเร็ว
