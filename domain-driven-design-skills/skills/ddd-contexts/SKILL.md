# DDD Contexts

> 🌐 English version: [English](SKILL.en.md)

## สถานการณ์ที่ควรใช้

- Subdomain จำแนกเสร็จแล้ว ต้องการออกแบบขอบเขต Bounded Context ของ Solution Space
- ต้องการสร้าง Ubiquitous Language สำหรับแต่ละ Context กำจัดจุดคลุมเครือของศัพท์
- `ddd-aggregates` รายงาน "Invariant ข้ามหลาย Context" หรือ `ddd-model-review` รายงาน "อัตราข้อขัดแย้งศัพท์ > 20%" ให้ใช้เป็นเป้าหมายการย้อนกลับ

## ความต้องการ Input

- **จำเป็น**: ตารางจำแนก Subdomain และคำประกาศ Domain หลัก (จาก `ddd-subdomains`), Event Stream และระบุจุดร้อน (จาก `ddd-discover`)
- **ไม่จำเป็น**: ข้อมูลองค์กร (ขอบเขตทีม, จังหวะการส่งมอบ), ศัพท์บัญชี (จาก `ddd-scope`)

## ขั้นตอน

1. **จัดกลุ่ม**: ใช้ขอบเขตความสอดคล้องและขอบตัวอักษรเป็นเกณฑ์ จัดกลุ่มความสามารถเป็นตัวเลือก Context ศัพท์ภายใน Context เดียวกันต้องมีความหมายเดียว
2. **กำหนดหน้าที่**: สำหรับแต่ละ Context ระบุหน้าที่ทางธุรกิจ, แนวคิดหลัก, Event หลัก และความเป็นเจ้าของข้อมูล
3. **สร้างภาษากลาง**: สำหรับศัพท์หลักแต่ละคำใน Context สร้างคำจำกัดความ (พร้อมตัวอย่างธุรกิจ 1 ตัวอย่าง) ระบุคำพ้องความหมายและคำต้องห้าม
4. **วาดขอบเขต**: ระบุว่าแนวคิดใดมีผลเฉพาะใน Context นี้เท่านั้น และแนวคิดใดต้องแปลเมื่อใช้ข้าม Context
5. **ความเป็นเจ้าของและ ADR**: ระบุทีมที่รับผิดชอบ, ผู้ตัดสินใจ, Owner ของสัญญา สร้าง ADR สำหรับการตัดสินใจขอบเขต (พร้อมเหตุผล, การเปรียบเทียบ, ความเสี่ยง, ทางเลือกอื่น)
6. **จัดการข้อขัดแย้ง**: จัดการศัพท์ที่มีชื่อเหมือนแต่ความหมายต่างกันข้าม Context — ให้กลยุทธ์การแปลหรือข้อเสนอแนะการเปลี่ยนชื่อ

## ผลลัพธ์

| ผลงาน                   | ข้อกำหนดโครงสร้าง                                                          |
| :----------------------- | :--------------------------------------------------------------------------- |
| สารบัญ Context           | ตาราง: ชื่อ Context, หน้าที่, ศัพท์หลัก, Event หลัก, ความเป็นเจ้าของข้อมูล, ทีมรับผิดชอบ |
| คลังคำศัพท์ภาษากลาง     | ตาราง: ศัพท์, คำจำกัดความ, ตัวอย่างธุรกิจ, Context ที่สังกัด, พ้องความหมาย, คำต้องห้าม, การจัดการข้อขัดแย้ง |
| รายการคำต้องห้าม         | ตาราง: คำห้ามใช้, เหตุผลที่ห้าม, คำแนะนำทดแทน                             |
| รายการ Boundary ADR       | แต่ละรายการมี: การตัดสินใจ, เหตุผล, การเปรียบเทียบ, ความเสี่ยง, ทางเลือกอื่น |
| กฎวิวัฒนาการภาษา        | รายการ: กระบวนการเพิ่ม/เปลี่ยนแปลง, บทบาทตรวจสอบ, กลยุทธ์เวอร์ชัน         |

## รายการตรวจสอบ

- [ ] ทุก Context มี "หน้าที่" และ "ไม่ใช่หน้าที่" ที่ชัดเจน
- [ ] ความเป็นเจ้าของข้อมูลไม่มีข้อขัดแย้ง การเข้าถึงข้าม Context ต้องผ่านสัญญา/การแปล
- [ ] ทุก Context มีอย่างน้อย 1 จุดเปรียบเทียบและความเสี่ยงที่ชัดเจน (ADR)
- [ ] ข้อขัดแย้งศัพท์ทั้งหมดได้รับการแก้ไขแล้ว (แปลหรือเปลี่ยนชื่อ)
- [ ] รายการคำต้องห้ามครอบคลุมการปนเปื้อนคำเทคนิค (Manager, Processor, Handler ฯลฯ) และคำธุรกิจที่คลุมเครือ
- [ ] หากมีการนำแนวคิดระหว่างทาง (เช่น ShippingRequest, OrderDraft, BookingIntent) เข้ามาในกระบวนการสั่งซื้อ/ธุรกรรม ได้ประกาศความสัมพันธ์กับ Aggregate หลักแล้ว (เลื่อนเป็น Aggregate อิสระ vs. เทียบเท่า VO ของ Aggregate หลัก) ทั้งสองทางเลือกถูกต้องแต่ **ต้องระบุและบันทึก ADR อย่างชัดเจน**

## การย้อนกลับ

- > 5 ศัพท์มีข้อขัดแย้งข้าม Context ที่ไม่สามารถประนีประนอมได้ → ย้อนกลับไป `ddd-discover` ความเข้าใจ Domain ยังไม่เพียงพอ
- ถูก trigger ย้อนกลับโดย `ddd-aggregates`: Invariant ข้ามหลาย Context → ความต้องการความสอดคล้องถูกตัดขาดโดยขอบเขต ต้องแบ่งใหม่
- ถูก trigger ย้อนกลับโดย `ddd-model-review`: ขอบเขต Aggregate ขัดแย้งกับขอบเขต Context หรืออัตราข้อขัดแย้งศัพท์ > 20%

## ตัวอย่าง

```text
@ddd-contexts
จากการจำแนก Subdomain และ Event Stream ต่อไปนี้ ช่วยออกแบบ Bounded Context:
- Core: การจองและการจัดการความขัดแย้ง
- Supporting: การจัดการทรัพยากรห้องประชุม
- Generic: ตัวตนและสิทธิ์ผู้ใช้
[วางตาราง Event Stream]
สร้าง สารบัญ Context, คลังคำศัพท์ภาษากลาง, Boundary ADR
```
