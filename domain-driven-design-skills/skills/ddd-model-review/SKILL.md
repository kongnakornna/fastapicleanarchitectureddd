# DDD Model Review

> 🌐 English version: [English](SKILL.en.md)

## สถานการณ์ที่ควรใช้

- การ Tactical Modeling เสร็จสมบูรณ์แล้ว ต้องการตรวจสอบ Quality Gate ของโมเดลภาพรวม
- มีผลงาน Modeling ที่มีอยู่ต้องการประเมินอย่างครอบคลุม (ใช้เป็นจุดเริ่มต้นอิสระได้)
- การตรวจสอบสุขภาพโมเดลเป็นระยะ: ทีมต้องการวัดคุณภาพโมเดลและระบุแนวโน้มการเสื่อมสภาพ

## ความต้องการ Input

- **จำเป็น**: ต้องการผลงานอย่างน้อย 3 รายการจากต่อไปนี้:
  - สารบัญ Context และคลังคำศัพท์ (จาก `ddd-contexts`)
  - เมトリกซ์ความสัมพันธ์ Context (จาก `ddd-context-map`)
  - สารบัญ Aggregate และตาราง Invariant (จาก `ddd-aggregates`)
  - สารบัญ Domain Event และนิยาม Service (จาก `ddd-domain-interactions`)
- **ไม่จำเป็น**: การจำแนก Subdomain (จาก `ddd-subdomains`), Event Stream (จาก `ddd-discover`), นิยาม Scope (จาก `ddd-scope`)

## ขั้นตอน

1. **ตรวจสอบความสอดคล้องของศัพท์**: สแกนการใช้ศัพท์ในทุกผลงาน ตรวจจับข้อขัดแย้งในการตั้งชื่อ, การเลื่อนไหลของคำจำกัดความ, ชื่อเหมือนความหมายต่างกันข้ามผลงาน
   - **เปรียบเทียบอุตสาหกรรม (ไม่บังคับแต่แนะนำ)**: หาก Domain ธุรกิจมีการ implement อ้างอิง open source ที่ครบถ้วน (เช่น โลจิสติกส์ Cargo, อีคอมเมิร์ซ Broadleaf, B2B Pyramid) ให้ใช้เป็นเกณฑ์เปรียบเทียบมิติที่ 9 ระบุทีละข้อ: การ **เบี่ยงเบนการหลอมรวม/แยก** ของโมเดลนี้เทียบกับอ้างอิง; **การระบุข้อจำกัดที่รู้อยู่แล้วของอ้างอิง** (เช่น ความทับซ้อน Activity/Status/Event); **Domain ในอนาคตที่ยังไม่ได้ Model แต่ควรพิจารณา** (เช่น Billing/Customer/Carrier)
2. **ตรวจสอบความสอดคล้องขอบเขต**: ตรวจสอบว่าขอบเขต Aggregate สอดคล้องกับขอบเขต Context หรือไม่ — Invariant ไม่ควรข้าม Context
3. **ตรวจสอบความสมบูรณ์**: ตรวจสอบว่า Event ทุกรายการใน Event Stream มีนิยามทางการในสารบัญ Event หรือไม่; ทุกคำสั่งมี Aggregate ที่รับผิดชอบหรือไม่
4. **วิเคราะห์การเชื่อมต่อ**: ประเมินระดับการเชื่อมต่อระหว่าง Context — ทิศทางการพึ่งพา, ปริมาณข้อมูลที่ใช้ร่วม, จำนวนการเรียกแบบ synchronous
5. **ให้คะแนน**: ให้คะแนน 0-10 สำหรับมิติดังต่อไปนี้: ความสอดคล้องศัพท์, ความสมเหตุสมผลขอบเขต, อัตราการแสดง Invariant, ความสมบูรณ์ของ Event, ระดับการเชื่อมต่อ; หากเปิดใช้การเปรียบเทียบอุตสาหกรรม เพิ่มมิติ "การเบี่ยงเบนจากการเปรียบเทียบ"
6. **รายการปัญหาและการย้อนกลับ**: สร้างปัญหาที่พบ, ผลกระทบ, หลักฐาน, แผนการแก้ไข และสร้างคำสั่งย้อนกลับตามเงื่อนไข

## ผลลัพธ์

| ผลงาน                       | ข้อกำหนดโครงสร้าง                                                                                              |
| :--------------------------- | :--------------------------------------------------------------------------------------------------------------- |
| ภาพรวมคะแนน                  | ตาราง: มิติ (ความสอดคล้องศัพท์, ความสมเหตุสมผลขอบเขต, อัตราการแสดง Invariant, ความสมบูรณ์ Event, ระดับการเชื่อมต่อ), คะแนน(0-10), เหตุผลหักคะแนนหลัก |
| รายการปัญหา                  | ตาราง: ปัญหา, ผลกระทบ, หลักฐาน (อ้างอิงผลงานและรายการเฉพาะ), แผนการแก้ไข, ลำดับความสำคัญ                     |
| รายงานเปรียบเทียบอุตสาหกรรม | (เฉพาะเมื่อเปิดใช้) ตาราง: รายการเปรียบเทียบ, การทำของอ้างอิง, การทำของโมเดลนี้, หลอมรวม/แยก/ตกหล่น, ยอมรับได้หรือไม่, ข้อเสนอแนะ |
| รายการการย้อนกลับ            | ตาราง: เงื่อนไขการกระตุ้น, Skill เป้าหมายการย้อนกลับ, คำอธิบาย                                                      |
| การตัดสินความพร้อมดำเนินการ | ข้อสรุป: พร้อม / ไม่พร้อม + รายการอุปสรรค                                                                          |

## รายการตรวจสอบ

- [ ] ทุกรายการที่หักคะแนนมีหลักฐานที่ตรวจสอบได้ (อ้างอิงผลงานและรายการเฉพาะ)
- [ ] เงื่อนไขการย้อนกลับชัดเจนและสามารถปฏิบัติได้
- [ ] คะแนนสามารถทำซ้ำได้ (Input เดียวกันได้คะแนนเท่ากัน)
- [ ] การตัดสินความพร้อมมีเกณฑ์ผ่าน/ไม่ผ่านที่ชัดเจน
- [ ] หาก Domain มีการ implement อ้างอิง open source ที่ได้รับการยอมรับ ได้ทำอย่างน้อย 1 รอบการเปรียบเทียบแล้ว; ผลลัพธ์ได้รับการบันทึกในรายการปัญหา

## การย้อนกลับ

Skill นี้เป็นตัวกระตุ้นหลักของปิดลูป feedback ตามผลการประเมิน trigger การย้อนกลับต่อไปนี้:

| เงื่อนไขการกระตุ้น               | ย้อนกลับไป                 | คำอธิบาย                                    |
| :-------------------------------- | :-------------------------- | :------------------------------------------ |
| ขอบเขต Aggregate ขัดแย้งกับขอบเขต Context | `ddd-contexts`              | Context ต้องแบ่งใหม่เพื่อรับความต้องการความสอดคล้อง |
| อัตราข้อขัดแย้งศัพท์ > 20%       | `ddd-contexts`              | นิยามภาษากลางไม่เพียงพอ                    |
| อัตราการแสดง Invariant < 60%     | `ddd-aggregates`            | Aggregate อาจเป็น Data Container แทนที่จะเป็นขอบเขตพฤติกรรม |
| รูปแบบการเชื่อมต่อไม่สอดคล้องกับแผนที่ Context | `ddd-context-map`           | ชั้น Tactics ค้นพบความต้องการเชื่อมต่อใหม่  |
| ความสมบูรณ์ Event < 70%           | `ddd-domain-interactions`   | สารบัญ Event ขาดหายหรือไม่ครอบคลุมกระบวนการสำคัญ |

**ป้องกันลูปไม่รู้จบ**: เส้นทางการย้อนกลับเดียวกันทำได้สูงสุด 3 ครั้ง หากครั้งที่ 3 ยัง trigger ให้ระบุเป็น "การตัดสินใจทางสถาปัตยกรรมที่ต้องใช้การแทรกแซงของมนุษย์"

## ตัวอย่าง

```text
@ddd-model-review
ช่วยประเมินคุณภาพภาพรวมของผลงาน Modeling ต่อไปนี้:
- สารบัญ Context: [วาง]
- สารบัญ Aggregate: [วาง]
- สารบัญ Domain Event: [วาง]
- เมトリกซ์ความสัมพันธ์ Context: [วาง]
สร้าง คะแนนตามมิติ, รายการปัญหา และข้อเสนอแนะการย้อนกลับ
```
