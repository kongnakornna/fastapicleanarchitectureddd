# DDD Context Map

> 🌐 English version: [English](SKILL.en.md)

## สถานการณ์ที่ควรใช้

- Bounded Context ออกแบบเสร็จแล้ว ต้องการออกแบบความร่วมมือและการเชื่อมต่อระหว่างกัน
- ต้องการระบุชัดเจนว่า "ใครพึ่งพาใคร ใช้รูปแบบใดในการเชื่อมต่อ สัญญาใครเป็นผู้รับผิดชอบ"
- `ddd-model-review` รายงาน "รูปแบบการเชื่อมต่อไม่สอดคล้องกับแผนที่" ให้ใช้เป็นเป้าหมายการย้อนกลับ

## ความต้องการ Input

- **จำเป็น**: สารบัญ Context (จาก `ddd-contexts`), จุดข้ามขอบเขตในระบุจุดร้อนของ Event Stream (จาก `ddd-discover`)
- **ไม่จำเป็น**: ตารางจำแนก Subdomain (จาก `ddd-subdomains` ใช้เพื่อเข้าใจน้ำหนักทางธุรกิจของ Context), วิธีการแลกเปลี่ยนข้อมูล/Interface/Message ปัจจุบัน, รูปแบบการทำงานร่วมกันของทีม

## ขั้นตอน

1. **ระบุความสัมพันธ์**: ระบุคู่ Context ทั้งหมด ระบุทิศทางการพึ่งพาและทิศทางข้อมูล/Event
2. **เลือกรูปแบบ**: เลือกรูปแบบการเชื่อมต่อสำหรับแต่ละคู่ความสัมพันธ์ — ACL (Anti-Corruption Layer), OHS (Open Host Service), PL (Published Language), Shared Kernel, Conformist, Customer-Supplier — พร้อมอธิบายเหตุผล
3. **กำหนดการแปล**: ระบุการแปล Input, การแปล Output, การจัดการความแตกต่างทางอรรถศาสตร์, กฎการจับคู่ Field
4. **ความเป็นเจ้าของสัญญา**: ระบุ Owner, ผู้บริโภค, กระบวนการเปลี่ยนแปลง, กลยุทธ์การเผยแพร่ สำหรับแต่ละสัญญา
5. **วิเคราะห์รูปแบบความล้มเหลว**: วิเคราะห์รูปแบบความล้มเช่น Timeout, Degradation, Idempotency, Retry, Compensation, Data Latency สำหรับแต่ละจุดเชื่อมต่อ
6. **กลยุทธ์เวอร์ชัน**: กำหนดกรอบเวลาความเข้ากันได้, กลยุทธ์การเลิกใช้, ความต้องการการทดสอบสัญญา, จังหวะการเผยแพร่

## ผลลัพธ์

| ผลงาน                    | ข้อกำหนดโครงสร้าง                                          |
| :------------------------ | :----------------------------------------------------------- |
| เมกซ์ความสัมพันธ์ Context | ตาราง: Upstream, Downstream, รูปแบบ, ข้อมูล/Event, ความเสี่ยง |
| เมกซ์ความเป็นเจ้าของสัญญา | ตาราง: สัญญา, Owner, ผู้บริโภค, กระบวนการเปลี่ยนแปลง, กลยุทธ์การเผยแพร่ |
| การตัดสินใจแปลและ ACL    | ตาราง: วัตถุ/Event, กฎการแปล, คำอธิบายความแตกต่างทางอรรถศาสตร์, ตำแหน่งที่ implement |
| รูปแบบความล้มเหลวและการบรรเทา | ตาราง: รูปแบบความล้มเหลว, ผลกระทบ, วิธีตรวจจับ, มาตรการบรรเทา, กลยุทธ์ชดเชย |
| กลยุทธ์เวอร์ชัน           | รายการ: กฎการตั้งชื่อเวอร์ชัน, กรอบเวลาความเข้ากันได้, กลยุทธ์การเลิกใช้, ความต้องการทดสอบสัญญา |

## รายการตรวจสอบ

- [ ] การโต้ตอบข้าม Context ทั้งหมดมีรูปแบบและความเป็นเจ้าของที่ชัดเจน
- [ ] Input ของ Domain หลักได้รับการปกป้องโดย ACL หรือขอบเขตการแปลที่เทียบเท่า
- [ ] ระบุรูปแบบความล้มเหลวอย่างน้อย 5 รูปแบบและให้มาตรการบรรเทาที่สามารถปฏิบัติได้
- [ ] ไม่มีการพึ่งพาแบบวงจร (หากมีต้องระบุเป็นความเสี่ยงและให้วิธีการแยกส่วน)
- [ ] กลยุทธ์เวอร์ชันครอบคลุมกรอบเวลาความเข้ากันได้ย้อนหลังและกระบวนการเลิกใช้

## การย้อนกลับ

- ตรวจจับการพึ่งพาแบบวงจร หรือ Context เดียวรับผิดชอบความสัมพันธ์ Upstream > 3 → ย้อนกลับไป `ddd-subdomains` หรือ `ddd-contexts` (อาจมี "God Context" หรือการจำแนก Subdomain ผิด)
- ถูก trigger ย้อนกลับโดย `ddd-model-review`: ชั้น Tactics ค้นพบความต้องการเชื่อมต่อใหม่ ไม่สอดคล้องกับแผนที่ปัจจุบัน
