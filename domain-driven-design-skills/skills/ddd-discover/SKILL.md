# DDD Discover

> 🌐 English version: [English](SKILL.en.md)

## สถานการณ์ที่ควรใช้

- ต้องการปรับทิศทางกระบวนการธุรกิจหลักและเบาะแสขอบเขต Domain อย่างรวดเร็ว
- ความต้องการระบุชัดแล้ว (จาก `ddd-scope` หรือ用户提供โดยตรง) ต้องการสำรวจว่าเกิดอะไรขึ้นภายใน Domain
- `ddd-contexts` รายงานว่า "ข้อขัดแย้งของศัพท์ไม่สามารถประนีประนอมได้" ให้ใช้เป็นเป้าหมายการย้อนกลับ

## ความต้องการ Input

- **จำเป็น**: คำอธิบายสถานการณ์ธุรกิจ (User Story, PRD, Work Order หรือ Output ของ `ddd-scope` ก็ได้)
- **ไม่จำเป็น**: ผู้มีส่วนร่วมหลักและระบบภายนอก, ข้อจำกัดทางธุรกิจและไม่ใช่เป้าหมาย (จาก `ddd-scope`)

## ขั้นตอน

1. **ระบุ Event**: มุมมอง "ข้อเท็จจริงที่เกิดขึ้นแล้ว" ตั้งชื่อ Domain Event เป็น **อดีตกาล** (เช่น OrderPlaced, PaymentReceived)
2. **เติมคำสั่ง**: สำหรับแต่ละ Event เพิ่มคำสั่งที่กระตุ้น, ผู้เริ่ม, ข้อมูล Input สำคัญ
3. **เรียงลำดับเวลา**: จัด Event ตาม Timeline ระบุทางแยก, การ rollback, เส้นทางผิดปกติ (อย่างน้อย 1 เส้นทางหลัก + 2 เส้นทางผิดปกติ)
4. **ระบุจุดร้อน**: ทำเครื่องหมาย Event ที่มีความถี่สูง, จุดที่ต้องการความสอดคล้องสูง, ขอบเขตข้ามระบบ, จุดที่อ่อนไหวต่อประสิทธิภาพ, จุดตรวจสอบกฎระเบียบ
5. **สร้างรายการจุดคลุมเครือ**: บันทึกข้อขัดแย้งของศัพท์, สถานะที่ไม่ชัดเจน, ความไม่ชัดเจนในความรับผิดชอบ ระบุ "ใครต้องยืนยัน"
6. **สร้างเบาะแสขอบเขต**: แยกกลุ่มความสามารถเบื้องต้นและขอบเขต Context ที่เป็นไปได้จากการจัดกลุ่ม Event และการกระจายจุดร้อน

## ผลลัพธ์

| ผลงาน           | ข้อกำหนดโครงสร้าง                                                           |
| :--------------- | :---------------------------------------------------------------------------- |
| ตาราง Event Stream | ตาราง: ลำดับ, ชื่อ Event (อดีตกาล), คำสั่งที่กระตุ้น, ผู้มีส่วนร่วม, Input/Output, ทางแยกผิดปกติ |
| รายการคำสั่งที่เป็นไปได้ | ตาราง: คำสั่ง, ผู้เริ่ม, ผลลัพธ์ที่คาดหวัง, ความต้องการ Idempotency      |
| รายการ Event ที่เป็นไปได้ | ตาราง: Event, ช่องข้อมูลสำคัญ, ข้าม Context หรือไม่, เผยแพร่ภายนอกหรือไม่ |
| ระบุจุดร้อน     | รายการ: จุดสอดคล้อง, จุดเชื่อมต่อ, จุดประสิทธิภาพ, จุดกฎระเบียบ          |
| รายการจุดคลุมเครือ | ตาราง: จุดคลุมเครือ, ผลกระทบ, ฝ่ายที่ต้องยืนยัน, ข้อเสนอแนะการตัดสินใจ |
| เบาะแสขอบเขต   | รายการ: กลุ่มความสามารถเบื้องต้นและขอบเขต Context ที่อาจเป็นไปได้       |

## รายการตรวจสอบ

- [ ] Event ตั้งชื่อเป็นอดีตกาล ฝ่ายธุรกิจเข้าใจได้
- [ ] มีอย่างน้อย 1 เส้นทางหลัก + 2 เส้นทางผิดปกติ/rollback
- [ ] จุดร้อนระบุขอบเขตข้ามระบบและจุดสอดคล้องสูงอย่างชัดเจน
- [ ] ทุกรายการในรายการจุดคลุมเครือระบุ "ใครต้องยืนยัน"
- [ ] เบาะแสขอบเขตสามารถนำไปใช้โดย `ddd-subdomains` ได้โดยตรง

## การย้อนกลับ

- Skill นี้ถูก trigger ย้อนกลับโดย `ddd-contexts`: เมื่อมี > 5 ศัพท์มีข้อขัดแย้งข้าม Context ที่ไม่สามารถประนีประนอมได้ แสดงว่าความเข้าใจ Domain ยังไม่เพียงพอ ต้องค้นพบใหม่

## ตัวอย่าง

```text
@ddd-discover
จาก Output scope ต่อไปนี้ ช่วยทำ Domain Discovery:
- ปัญหา: กระบวนการหลังการขายคำสั่งซื้อยุ่งเหยิง
- เป้าหมาย: รองรับการคืนเงิน, การแลกสินค้า, การจัดการร้องเรียน
- ไม่ใช่เป้าหมาย: ไม่เกี่ยวกับกระบวนการสั่งซื้อทางบวก
สร้าง ตาราง Event Stream, คำสั่ง/Event ที่เป็นไปได้, ระบุจุดร้อน และรายการจุดคลุมเครือ
```
