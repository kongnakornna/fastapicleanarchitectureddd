# 02 — ผลผลิต ddd-discover (Blind Run)

> ข้อมูลนำเข้า: `00-fuzzy-prompt.md` + `01-ddd-scope.out.md`
> ไฟล์นี้เป็นผลผลิตจากการจำลองการดำเนินงานของ `ddd-discover` ใน blind run โดย **ไม่ได้อ้างอิง** เอกสาร ground truth ใน `reference/` ใดๆ
> การตั้งชื่อ Event ใช้ **กาลในอดีต**; ต้องครอบคลุมอย่างน้อย 1 เส้นทางหลัก + 2 เส้นทางข้อผิดพลาด/ย้อนกลับ

## รายการผู้สมัครคำสั่ง

| คำสั่ง                     | ผู้ริเริ่ม | ผลลัพธ์ที่คาดหวัง                       | ความต้องการ idempotent |
| :----------------------- | :------------ | :----------------------------- | :------------------------------------------------- |
| `SubmitShippingRequest`  | ลูกค้า          | สร้างเลขที่ความต้องการ                   | ใช้ clientRequestId ทำให้ idempotent            |
| `QueryRoutingOptions`    | ระบบ          | ตัวเลือกที่ทำได้หลายแบบ                   | อ่านอย่างเดียว idempotent โดยธรรมชาติ                                     |
| `SelectOption`           | ลูกค้า          | ตัวเลือกที่เลือก                       | ใช้เลขที่ความต้องการ + เลขที่ตัวเลือกทำให้ idempotent                          |
| `ConfirmBooking`         | เจ้าหน้าที่จองระวาง / ระบบ | สร้างคำสั่งซื้อ / สินค้าหนึ่งรายการ            | ใช้เลขที่ความต้องการทำให้ idempotent (หนึ่งคำสั่งซื้อหนึ่งครั้ง)                         |
| `AssignRoute`            | ระบบ          | กำหนดเส้นทางให้คำสั่งซื้อ             | อนุญาตให้เขียนทับ ต้องมี version                                |
| `RegisterHandling(type)` | ฝ่ายปฏิบัติการท่าเรือ    | เขียนข้อเท็จจริงปฏิบัติการหนึ่งรายการ               | ใช้ (คำสั่งซื้อ + เลกการเดินเรือ + ประเภทปฏิบัติการ + เวลาที่เกิด + ท่าเรือ) ทำให้ idempotent |
| `RequestReroute`         | เจ้าหน้าที่บริการลูกค้า / ระบบ   | กระตุ้นกระบวนการวางแผนใหม่               | ใช้คำสั่งซื้อ + หมายเลขเวอร์ชันข้อผิดพลาดทำให้ idempotent                            |
| `QueryTracking`          | ลูกค้า          | ตำแหน่งปัจจุบัน / สถานะ / ETA / ขั้นตอนถัดไป | อ่านอย่างเดียว                                               |

## การระบุจุดร้อน

### จุดร้อนเรื่อง consistency

- **คีย์ตัดรายการซ้ำซ้อน**ของข้อเท็จจริงปฏิบัติการต้องมีเสถียรภาพ: ชุดชุดของ (คำสั่งซื้อ + ประเภทปฏิบัติการ + เวลาที่เกิด + ท่าเรือ + เลกการเดินเรือ) ต้องได้รับการยอมรับจากทั้งระบบ ไม่เช่นนั้นข้อเท็จจริงเดียวจะถูกนับซ้ำหลายครั้ง
- การตัดสิน "ลงผิดท่า / ควรไปที่ไหน" ต้องการ **แผนเส้นทางปัจจุบัน** และ **การปฏิบัติการจริง** สามารถเทียบกันได้ในเวลาเดียวกัน; เกี่ยวข้องกับ consistency ที่เข้มงวดของลำดับเวอร์ชันเส้นทางและลำดับเวลาถึงของการปฏิบัติการ
- หลังจากข้อมูลล่าช้าเข้าระบบแล้ว ต้องเรียงตาม `occurredAt` แล้ว **คำนวณสถานะที่สืบทอดมาใหม่** (ตำแหน่ง / ETA / ข้อผิดพลาด)

### จุดร้อนเรื่องการเชื่อมต่อ

- อินเทอร์เฟซกับ **ผู้ให้ข้อมูลเส้นทางภายนอก** เป็นขอบเขตนอกที่เปราะบางที่สุดของระบบ: ต้องมี Anti-Corruption Layer การใช้ซ้ำกันในทั้งสองจุดคือการสั่งและการวางแผนใหม่ แต่บริบทการเรียกใช้ต่างกัน (จุดหนึ่งบนพื้นฐานของความต้องการ อีกจุดบนพื้นฐานของตำแหน่งปัจจุบัน)
- อินเทอร์เฟซกับ **ฝ่ายปฏิบัติการท่าเรือภายนอก** หลายช่องทาง (Web/API/ไฟล์) asynchronous ไม่น่าเชื่อถือ: ต้องมีรูปแบบ "การดูดซับ + การตัดรายการซ้ำซ้อน + การกักกัน" สามขั้นตอน

### จุดร้อนเรื่องประสิทธิภาพ

- ที่พีค 500,000 Event/วัน เฉลี่ยประมาณ **5.8 QPS, ที่พีคประมาณ 50–100 QPS** (การส่งติดกันในช่วงสั้น); รวมกับยอดสอบถามที่พีค 200 QPS; การลงทะเบียนเข้าระบบที่ต้อง asynchronous และ partitioned
- เส้นทางสอบถามของลูกค้า (ตำแหน่งปัจจุบัน / สถานะ / ETA / ขั้นตอนถัดไป) เป็นการอ่านความถี่สูง; ควรนำโมเดลการอ่านมาจา Event ที่สืบทอดมา ห้าม aggregate แบบเรียลไทม์

### จุดร้อนเรื่อง compliance / การตรวจสอบ

- ข้อเท็จจริงปฏิบัติการเมื่อเขียนแล้วห้าม "ลบเงียบ": การแก้ไขต้องเขียนทับด้วยข้อเท็จจริงเวอร์ชันใหม่และเก็บรักษาลูกตรวจสอบไว้
- การย้อนเวลากลับของข้อมูลล่าช้าอาจทำให้สถานะที่สืบทอดมาในอดีตถูกแก้ไข ต้องมีการตรวจสอบอย่างครบถ้วน

## ใบนำทางขอบเขต (สำหรับการใช้งานโดย `ddd-subdomains` / `ddd-contexts`)

บนพื้นฐานของการจัดกลุ่ม Event การกระจายจุดร้อน และการแบ่งทีม, ระบุ **4 กลุ่มผู้สมัครชุดความสามารถ** ได้เบื้องต้น:

1. **ความสามารถด้านการจอง** (หลัก): จากความต้องการขนส่งไปยังการยืนยันคำสั่งซื้อ แล้วไปยังการกำหนดและกำหนดใหม่ของเส้นทาง; มีกฎการคำนวณสถานะที่เชื่อถือได้สำหรับ "สินค้าหนึ่งรายการ" ทีมที่เกี่ยวข้อง: ทีมจอง/บริการลูกค้า
2. **ความสามารถด้านการปฏิบัติการท่าเรือ** (สนับสนุนแต่สำคัญ): ดูดซับข้อเท็จจริงการปฏิบัติการภายนอกแบบ asynchronous ทำ idempotent, การตรวจสอบ, การกักกัน; เผยแพร่เฉพาะ "ข้อเท็จจริงปฏิบัติการได้รับการยอมรับ/ถูกปฏิเสธ" ทีมที่เกี่ยวข้อง: ทีมเชื่อมต่อข้อมูลการปฏิบัติการท่าเรือ
3. **ความสามารถด้านการสอบถามของลูกค้า** (สนับสนุน): โมเดลการอ่านสำหรับลูกค้า รวมข้อมูลการจองและข้อเท็จจริงการปฏิบัติการ สืบทอดตำแหน่ง/สถานะ/ETA/ขั้นตอนถัดไป ทีมที่เกี่ยวข้อง: ทีม frontend ฝั่งลูกค้า
4. **ความสามารถด้านการวางแผนเส้นทาง** (ทั่วไป, จัดซื้อจากภายนอก): ผู้ให้ข้อมูลภายนอกจัดหาตัวเลือกที่ทำได้; ระบบนี้ไม่สร้างเอง เรียกผ่าน Anti-Corruption Layer เท่านั้น

**ความสัมพันธ์ข้ามขอบเขตที่สำคัญ**:

- การจอง → การปฏิบัติการท่าเรือ: การจองส่ง "เส้นทางถูกกำหนดแล้ว" การปฏิบัติการส่งกลับ "ข้อเท็จจริงปฏิบัติการ"
- การจอง ← การปฏิบัติการท่าเรือ: การสืบทอดข้อผิดพลาด (ลงผิดท่า) มาจากฝั่งการจองโดยบริโภคข้อเท็จจริงปฏิบัติการ
- การสอบถามลูกค้า ← การจอง + การปฏิบัติการท่าเรือ: aggregate อ่านอย่างเดียว
- การจอง ↔ การวางแผนเส้นทาง: ร้องขอ/ตอบสนองแบบ sync, แยกออกจากกันด้วย Anti-Corruption Layer
