# 08 — ผลลัพธ์ ddd-model-review (Blind Run, การตรวจสอบภายใน)

> ข้อมูลนำเข้า: `01`~`07`
> ไฟล์นี้เป็นผลลัพธ์จากการ **ตรวจสอบความสอดคล้องภายใน** ของ `ddd-model-review` ใน blind run — ตรวจสอบจากผลลัพธ์ของตัวเองเท่านั้น **ไม่ใช้** ground truth จาก `reference/`
> การเปรียบเทียบกับ ground truth และการให้คะแนนอยู่ใน `scoring/scorecard.md`

## มิติการให้คะแนนและผลคะแนน

สเกลการให้คะแนน: 0=ขาดอย่างรุนแรง, 1=มีข้อบกพร่องชัดเจน, 2=ยอมรับได้แต่มีโอกาสปรับปรุง, 3=ผ่านเกณฑ์, 4=ดีเยี่ยม

| มิติ | ผลคะแนน | ความเห็น |
| :--- | :--- | :--- |
| 1. ความชัดเจนของขอบเขตและเป้าหมายที่ไม่ใช่ | 4 | เป้าหมาย 5 รายการ เป้าหมายที่ไม่ใช่ 4 รายการ ข้อจำกัด 9 รายการ โครงสร้างสมบูรณ์; เป้าหมายที่ไม่ใช่และการพึ่งพาภายนอกระบุชัดเจน |
| 2. ความครอบคลุมของ Event Storm | 4 | เส้นทางหลัก 14 ขั้นตอน + กลุ่มข้อผิดพลาด 3 ชุด (A/B/C) รวมสถานการณ์ยาก 2 กรณีคือการขนถ่ายผิดและการมาถึงสาย |
| 3. ความสอดคล้องของคำศัพท์ (ข้าม Context) | 3 | `Shipment` / `HandlingFact` / `TrackingView` มีคำนิยามเดียวในแต่ละ Context; ตารางคำศัพท์ต้องห้ามระบุ 5 ประเภทการปนเปื้อนทั่วไป ยังไม่ได้คำนวณอัตราความขัดแย้งเชิงตัวเลข — ดูคร่าวๆ อัตราความขัดแย้ง < 10% |
| 4. ขอบเขตของ Context | 3.5 | 4 Context + 1 สันนิษฐาน (PortDirectory) การแบ่งหน้าที่ชัดเจน; ADR-01/02/03/04 ครอบคลุมการตัดสินใจที่สำคัญ หักคะแนน: การแจ้งเตือนลูกค้ายังไม่แยกเป็น Context อิสระ |
| 5. ความสมเหตุสมผลของ Context Map | 4 | เมทริกซ์ความสัมพันธ์ + กลยุทธ์ ACL + การลดระดับเมื่อเกิดความล้มเหลวครบถ้วน; มีรูปแบบ Customer-Supplier / OHS / ACL ครบทั้งสามแบบ |
| 6. ความสามารถในการแสดงออกของ Aggregate และ Invariant | 3.5 | Invariant 11 รายการ constraint เข้มงวด 10 รายการ; I-1~I-11 สอดคล้องกับ Aggregate ชัดเจน; ยังถกเถียงได้ว่า Route ควรแยกเป็น Aggregate อิสระหรือไม่ |
| 7. Domain Event และปฏิสัมพันธ์ | 4 | ตารางเผยแพร่-สมัครรับ คีย์ idempotent กระแสข้อมูล 3 สถานการณ์ครบถ้วน; ไม่พลาดสถานการณ์ยากที่สุดคือการเล่นซ้ำย้อนหลังจากข้อมูลมาถึงสาย |
| 8. สามารถสืบย้อนกลับเป้าหมายทางธุรกิจได้ | 4 | ทุกความสามารถหลัก C1~C13 สามารถเชื่อมโยงกับเป้าหมาย 1~5; เป้าหมายที่ไม่ใช่ไม่ถูกแตะต้องโดยไม่รู้ตัว |
| **ถ่วงน้ำหนักรวม** | **3.8 / 4** | โครงสร้างโดยรวมสมดุล ไม่มีห่วงโซ่ที่ขาดชัดเจน; การปรับปรุงเล็กน้อยอยู่ที่การตรวจสอบคำศัพท์แบบครบชุดและการแยก Context การแจ้งเตือนลูกค้าให้เป็นอิสระ |

## รายการปัญหา

| รหัส | ปัญหา | ผลกระทบ | Skill ที่ควรย้อนกลับ | ความรุนแรง |
| :--- | :--- | :--- | :--- | :--- |
| P1 | `RouteCandidate` ถูกระบุเป็น "Aggregate" ใน `06-aggregates` แต่จริงๆ เป็น VO/ร่างภายในของ Booking | ผู้อ่านอาจเข้าใจผิดว่าต้องมี Repository | `ddd-aggregates` | ต่ำ |
| P2 | ช่องทางการแจ้งเตือนลูกค้ายังไม่แยกเป็น Context อิสระ กระจัดกระจายอยู่ในคำอธิบายของ Tracking/Booking | การแยกออกในภายหลังทำได้ยาก | `ddd-contexts` | ต่ำ |
| P3 | ยังไม่ได้ระบุรายการ HandlingType ทั้งหมด (สันนิษฐาน 6 ประเภทแต่ยังไม่ล็อก) | โรงงานและกฎตรวจสอบขาดข้อมูลนำเข้าสุดท้าย | `ddd-discover` (เพิ่มข้อมูลธุรกิจ) | ปานกลาง |
| P4 | อัลกอริทึมการคำนวณ `NextExpectedAction` มีคำอธิบายเพียงประโยคเดียว ไม่อธิบายว่าเมื่อ route v(n+1) เพิ่งเปลี่ยนแล้วจัดการกับสถานะ "อยู่ระหว่างการขนส่ง" อย่างไร | พฤติกรรมสถานะชายขอบคลุมเครือ | `ddd-domain-interactions` | ปานกลาง |
| P5 | จุดยึดสำหรับการเล่นซ้ำย้อนหลังจากข้อมูลมาถึงสาย (เริ่มจากจุดเริ่มต้นของคำสั่งซื้อ หรือจาก handling ล่าสุดที่ไม่ได้รับผลกระทบ) ยังไม่ชัดเจน | ความซับซ้อนของการคำนวณสถานะใหม่ยังไม่ล็อก | `ddd-aggregates` / `ddd-domain-interactions` | ปานกลาง |
| P6 | `PortDirectory` สันนิษฐานว่ามีอยู่ แต่ไม่ชัดเจนว่าสังกัด Context ไหน (Supporting หรือ Generic) | ข้อมูลหลักของท่าเรือหลุดจากการจัดการ | `ddd-subdomains` | ต่ำ |

## การตัดสินใจกระตุ้นการย้อนกลับ

เทียบกับเงื่อนไขการกระตุ้นทั่วไปของ `ddd-model-review`:

| เงื่อนไขการกระตุ้น | สถานะปัจจุบัน | กระตุ้นหรือไม่ |
| :--- | :--- | :--- |
| ขอบ Aggregate ขัดแย้งกับขอบ Context | ไม่พบ (Shipment อยู่ใน Booking, HandlingFact อยู่ใน Handling, TrackingView อยู่ใน Tracking) | ไม่ |
| อัตราความขัดแย้งของคำศัพท์ > 20% | ประเมิน < 10% | ไม่ |
| อัตราการแสดงออกของ Invariant < 60% | Invariant 11 รายการสอดคล้องกับ Aggregate 4 ชุด ครอบคลุมทั่วถึง | ไม่ |
| รูปแบบการเชื่อมต่อไม่สอดคล้องกับ Context Map | OHS+ACL+CS สอดคล้องกับตำแหน่งของโดเมนย่อย | ไม่ |
| ความครบถ้วนของ Event < 70% | Booking 11 + Handling 4 = 15 Event ครอบคลุมเส้นทางหลัก + ข้อผิดพลาด + เล่นซ้ำ | ไม่ |

**ข้อสรุป: ไม่มีการกระตุ้นย้อนกลับเชิงระบบ** P1–P6 เป็น **การปรับปรุงเล็กน้อย** ไม่ต้องย้อนกลับทั้งห่วงโซ่

## ข้อเสนอแนะในการปรับปรุง (การแก้ไขเพิ่มเติมที่ไม่กระตุ้นการย้อนกลับ)

1. ย้าย `RouteCandidate` ออกจากตาราง Aggregate ไปไว้ในส่วน VO ของ Shipment และเน้น "อายุสั้น"
2. เพิ่ม Context ที่เป็นไปได้ที่ห้า "การแจ้งเตือนลูกค้า" ใน `04-contexts` แม้รุ่นนี้จะไม่แยกตัวออกมาเองก็ใส่ไว้ในแผนงาน
3. ยืนยันรายการ enum สุดท้ายของ `HandlingType` กับฝ่ายธุรกิจ; ถ้าต้องรวม `customs/inspection` ก็ขยาย I-8
4. เพิ่มกลยุทธ์ที่ชัดเจน 1 ย่อหน้าสำหรับ "จุดยึดสำหรับการเล่นซ้ำย้อนหลังจากข้อมูลมาถึงสาย" ใน `07-domain-interactions` (แนะนำให้ใช้ "handling ล่าสุดที่ไม่ได้รับผลกระทบ" เป็นจุดยึด)
5. ใส่ `PortDirectory` เข้าไปในโดเมนย่อย Supporting อย่างชัดเจน; ถ้าเป็นคลังคำศัพท์ภายนอกก็ย้ายไปเป็น Generic

## ความพร้อมของผู้บริโภคปลายน้ำ

| ผู้บริโภค | ความพร้อม |
| :--- | :--- |
| ทีมพัฒนา (Booking/Handling/Tracking 3 กลุ่ม) | พร้อม: สัญญา Event คีย์ idempotent อินเทอร์เฟซ Repository ครบถ้วน |
| การเชื่อมต่อภายนอก (Pathfinder / ฝ่ายปฏิบัติงาน) | พร้อม: กฎ ACL และกลยุทธ์การลดระดับชัดเจน |
| ฝ่ายปฏิบัติการ / ฝ่ายบริการลูกค้า | พร้อม: กลุ่ม Event ความผิดปกติและจุดกระตุ้นการแจ้งเตือนชัดเจน |
| การตรวจสอบและให้คะแนน | พร้อม: เข้าสู่ `scoring/scorecard.md` เพื่อเปรียบเทียบกับ ground truth |
