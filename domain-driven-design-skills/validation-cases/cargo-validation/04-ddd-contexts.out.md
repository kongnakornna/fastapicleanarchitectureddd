# 04 — ผลลัพธ์ ddd-contexts (Blind Run)

> ข้อมูลนำเข้า: `01-ddd-scope.out.md` + `02-ddd-discover.out.md` + `03-ddd-subdomains.out.md`
> ไฟล์นี้เป็นผลลัพธ์จากการจำลองการทำงานของ `ddd-contexts` ใน blind run โดย **ไม่ได้อ้างอิง** วัสดุ ground truth ใน `reference/` ใดๆ

## สารบัญ Bounded Context

| Context | โดเมนย่อยที่สังกัด | ขอบเขตความรับผิดชอบ (รวม/ไม่รวม) | คำศัพท์สำคัญ | ทีมที่รับผิดชอบ |
| :--- | :--- | :--- | :--- | :--- |
| **Booking บริบทการจอง** | Shipping & Tracking (Core) | รวม: การรับคำขอขนส่ง การนำเสนอตัวเลือก การยืนยันคำสั่งซื้อ การกำหนดเส้นทางและการกำหนดใหม่ การคำนวณสถานะที่เชื่อถือได้ของการขนส่งหนึ่งรายการ การตัดสินการขนถ่ายผิดและความล่าช้า การคำนวณ ETA ไม่รวม: การเก็บรักษาข้อมูลดิบของการปฏิบัติงาน มุมมองการอ่านของลูกค้า ข้อมูลเส้นทางจริง | คำขอขนส่ง คำสั่งซื้อ (การขนส่งหนึ่งรายการ) เส้นทาง เวอร์ชันเส้นทาง การขนถ่ายผิด ETA | ทีมจอง/บริการลูกค้า |
| **Handling บริบทการปฏิบัติงาน** | Handling Ingestion (Supporting) | รวม: ทางเข้าลงทะเบียนการปฏิบัติงาน การตัดซ้ำ idempotent การตรวจสอบฟิลด์ การกักกันข้อมูลผิดกฎหมาย การลงทะเบียนย้อนหลัง; เผยแพร่เฉพาะ "ข้อเท็จจริงการปฏิบัติงานได้รับการยอมรับ/ถูกปฏิเสธ" ให้ภายนอก ไม่รวม: การคำนวณสถานะ การตัดสินความผิดปกติ (เป็นหน้าที่ของ Booking) | ข้อเท็จจริงการปฏิบัติงาน ประเภทการปฏิบัติงาน เวลาที่เกิด ท่าเรือ ช่วงเรือ คีย์ตัดซ้ำ | ทีมเชื่อมต่อข้อมูลการปฏิบัติงานท่าเรือ |
| **Tracking บริบทการติดตาม** | Customer Tracking View (Supporting) | รวม: มุมมองการอ่านแบบรวมสำหรับลูกค้า (ตำแหน่ง/สถานะ/ขั้นตอนถัดไป/ETA) ไม่รวม: "สิทธิ์การตัดสินใจ" ของกฎธุรกิจใดๆ; ผลลัพธ์ทั้งหมดอ้างอิงจาก Event ที่ Booking เผยแพร่ | ตำแหน่ง ขั้นตอนถัดไปที่คาดหวัง ETA มุมมองการติดตาม | ทีม frontend สำหรับลูกค้า |
| **Pathfinder บริบทการวางแผนเส้นทาง (ภายนอก)** | Routing / Pathfinding (Generic) | รวม: การคำนวณตัวเลือกที่เป็นไปได้โดยผู้ให้ข้อมูลภายนอก ฝั่งเราเรียกผ่าน ACL โดยป้อนจุดเริ่มต้น/จุดหมาย+เวลาถึงล่าสุด (หรือตำแหน่งปัจจุบัน) และรับตัวเลือกที่เป็นไปได้กลับมา | ตัวเลือกที่เป็นไปได้ ช่วงเรือ ตารางเดินเรือ | ผู้ให้บริการภายนอก (ฝ่ายบูรณาการของเราเชื่อมต่อ) |

## คำศัพท์ Ubiquitous Language (ตามแต่ละ Context)

### Booking Context

| คำศัพท์ | นิยาม (ความหมายเดียวในบริบทนี้) | Event / คำสั่งที่เกี่ยวข้อง |
| :--- | :--- | :--- |
| คำขอขนส่ง ShippingRequest | ความต้องการเบื้องต้นของลูกค้าก่อนยืนยันคำสั่งซื้อเกี่ยวกับจุดเริ่มต้น/จุดหมาย/เวลาถึงล่าสุด; อาจตรงกับตัวเลือกที่เป็นไปได้หลายรายการ | SubmitShippingRequest, ShippingRequestSubmitted |
| คำสั่งซื้อ / การขนส่งหนึ่งรายการ Shipment | สัญญาการขนส่งจริงหนึ่งรายการที่เกิดขึ้นหลังจากลูกค้ายืนยันตัวเลือก (มุมมอง Aggregate ในบริบทนี้) | ConfirmBooking, ShipmentBooked |
| เส้นทาง Route | การจัดที่สามารถดำเนินการได้ "จากจุดหนึ่งไปอีกจุดหนึ่ง ประกอบด้วยช่วงเรือหลายช่วง" พร้อมหมายเลขเวอร์ชัน; คำสั่งซื้อหนึ่งรายการสามารถมีหลายเวอร์ชันตลอดวงจรชีวิต | AssignRoute, RouteAssigned, RouteReassigned |
| เวอร์ชันเส้นทาง RouteVersion | หมายเลขอัปเดตของเส้นทางภายใต้คำสั่งซื้อเดียวกัน | RouteAssigned.version |
| ข้อเท็จจริงการปฏิบัติงานที่เกิดแล้ว HandledFact | ข้อเท็จจริงการปฏิบัติงานของคำสั่งซื้อนี้ที่ได้รับการยอมรับและเผยแพร่โดย Handling Context | ← งานที่ได้รับการยอมรับจาก Handling |
| การขนถ่ายผิด Misrouting | การขนถ่ายจริง ≠ ท่าเรือที่ควรขนถ่ายตามเวอร์ชันเส้นทางปัจจุบัน | CargoMisroutedDetected |
| ความล่าช้า Delay | จุดเวลาของการปฏิบัติงานที่เกิดจริงล่าช้ากว่าตารางเส้นทางเกินเกณฑ์ที่กำหนด | (อนุมานได้) |
| ETA | เวลาจัดส่งโดยประมาณที่คำนวณจากเส้นทางที่เหลือ; คำนวณใหม่ทุกครั้งที่มีข้อเท็จจริงการปฏิบัติงานใหม่ | ETARecalculated |
| การวางแผนใหม่ Rerouting | การสร้างเส้นทางใหม่จาก "ตำแหน่งจริงปัจจุบัน" ไปยังจุดหมายหลังการขนถ่ายผิดหรือการเปลี่ยนแปลงของลูกค้า | RequestReroute, RouteReassigned |

### Handling Context

| คำศัพท์ | นิยาม | Event / คำสั่งที่เกี่ยวข้อง |
| :--- | :--- | :--- |
| ข้อเท็จจริงการปฏิบัติงาน HandlingFact | การปฏิบัติงานจริงหนึ่งรายการที่ท่าเรือหนึ่งในเวลาหนึ่งสำหรับคำสั่งซื้อหนึ่ง (รับของ/ขนขึ้น/ขนถ่าย/ถึงท่า/เคลื่อนย้าย/รับมอบ) ไม่สามารถแยกย่อยได้อีก | RegisterHandling |
| ประเภทการปฏิบัติงาน HandlingType | กลุ่มค่าแบบ enum (กลุ่มค่าจริงรอการยืนยันจากฝ่ายธุรกิจ) | — |
| คีย์ตัดซ้ำ DeduplicationKey | ทูเพิล (คำสั่งซื้อ + ประเภทการปฏิบัติงาน + ท่าเรือ + เวลาที่เกิด + ช่วงเรือ) | DuplicateHandlingRejected |
| มาถึงสาย LateArrival | ข้อเท็จจริงการปฏิบัติงานที่เวลามาถึงระบบ >> เวลาที่เกิดจริง | LateHandlingIngested |
| การกักกัน Quarantine | บัฟเฟอร์ที่ข้อเท็จจริงการปฏิบัติงานที่ไม่ผ่านการตรวจสอบฟิลด์/กฎธุรกิจเข้ามา รอการตรวจสอบด้วยตนเอง | InvalidHandlingQuarantined |
| ข้อเท็จจริงการปฏิบัติงานที่ได้รับการยอมรับ AcceptedHandling | ข้อเท็จจริงการปฏิบัติงานที่ผ่านทั้ง idempotency และการตรวจสอบ เผยแพร่ให้ภายนอก | (Event เผยแพร่ภายนอก) |

## ตารางคำศัพท์ต้องห้าม (Anti-Terms)

| คำที่ใช้ | เหตุผลที่ห้ามใช้ | ควรใช้คำว่า |
| :--- | :--- | :--- |
| "สถานะ" ที่ใช้ร่วมกันทั่วไประหว่าง Context | แต่ละ Context มีความหมายของสถานะต่างกัน ทำให้สับสน | Booking พูด "สถานะคำสั่งซื้อ/เวอร์ชันเส้นทาง"; Tracking พูด "มุมมองการติดตาม"; Handling พูด "ข้อเท็จจริงการปฏิบัติงานได้รับการยอมรับแล้วหรือยัง" |
| "Event" (ใช้เพียงอย่างเดียว) | ต้องแยก "ข้อเท็จจริงการปฏิบัติงาน" (ข้อเท็จจริงทางธุรกิจ) ออกจาก "Domain Event" (สิ่งที่เผยแพร่) | ใช้ชื่อแยกกันคือ ข้อเท็จจริงการปฏิบัติงาน / Domain Event |
| คำว่า "เส้นทาง" ปรากฏใน Pathfinder | เส้นทางเป็นแนวคิดภายในของ Booking; สิ่งที่ภายนอกส่งกลับคือ "ตัวเลือกที่เป็นไปได้" | ตัวเลือกที่เป็นไปได้ (ภายนอก) → เส้นทาง (ภายใน หลัง ACL) |
| "การตัดสิน/การระบุ/การวางแผนใหม่" ปรากฏใน Tracking | Tracking ไม่มีสิทธิ์ตัดสิน | แสดงใน Booking |
| "การขนถ่ายผิด/ความล่าช้า" ปรากฏใน Handling | Handling ไม่ตัดสินความผิดปกติ | แสดงใน Booking |

## การตัดสินใจขอบเขต ADR

### ADR-01: การตัดสินความผิดปกติเป็นหน้าที่ของ Booking ไม่ใช่ Handling

- **ตัวเลือก A**: Handling ตัดสิน "การขนถ่ายผิด" ทันทีที่รับข้อเท็จจริงการปฏิบัติงาน
- **ตัวเลือก B (เลือก)**: Handling รับผิดชอบเฉพาะการดูดซับ idempotent เท่านั้น Booking สมัครรับ Event "ข้อเท็จจริงการปฏิบัติงานที่ได้รับการยอมรับ" แล้วตัดสินการขนถ่ายผิดโดยอิงจากเวอร์ชันเส้นทางปัจจุบัน
- **เหตุผล**: การตัดสินต้องใช้ "เวอร์ชันเส้นทางปัจจุบัน" ซึ่งอยู่ใน Booking การย้ายกฎไปที่ Booking ทำให้มั่นใจได้ว่ามีมาตรฐานเดียว ป้องกัน Handling คัดลอกข้อมูลเส้นทาง; ในขณะเดียวกันก็ให้ Handling ยังคงเป็นสากลและซับซ้อนน้อยในแง่ธุรกิจ

### ADR-02: มุมมอง Tracking อ่านอย่างเดียว ห้ามมีการตัดสินใจใดๆ

- **ตัวเลือก A**: คัดลอก "การตัดสินการขนถ่ายผิด/การคำนวณ ETA" ไปไว้ใน Tracking เพื่อเพิ่มประสิทธิภาพการอ่าน
- **ตัวเลือก B (เลือก)**: Tracking คำนวณมุมมองจาก Event ที่ Booking เผยแพร่เท่านั้น
- **เหตุผล**: ป้องกันกฎหลุดลอย; Tracking อยู่ภายใต้ทีม frontend การเก็บกฎไว้จะทำให้สามทีมต้องแก้ไขตรรกะธุรกิจของกันและกัน

### ADR-03: สร้าง ACL สำหรับ Pathfinder

- **ตัวเลือก A**: ฟิลด์ภายนอกผ่านตรงเข้าสู่โมเดลหลัก เชื่อมต่อได้เร็ว
- **ตัวเลือก B (เลือก)**: โมเดลหลักยอมรับเฉพาะคำศัพท์ภายใน "ร่างเส้นทาง" เท่านั้น; ACL รับผิดชอบการแปลง/ความเข้ากันได้ของเวอร์ชัน/การลดระดับ
- **เหตุผล**: อินเทอร์เฟซภายนอกมีประวัติการเปลี่ยนแปลงมาแล้ว และฝ่ายธุรกิจระบุชัดว่า "ไม่ต้องการให้การเปลี่ยนแปลงของพวกเขาเจาะระบบของเรา"

### ADR-04: การขนส่งหนึ่งรายการ (Shipment) และคำขอขนส่ง (ShippingRequest) แยกเป็นคนละแนวคิด

- **ตัวเลือก A**: คำขอขนส่งอัปเกรดเป็นคำสั่งซื้อโดยตรง ส่งปุ๊บเป็นคำสั่งซื้อปั๊บ
- **ตัวเลือก B (เลือก)**: คำขอขนส่งเป็นแนวคิดอิสระในขั้นตอนค้นหาตัวเลือก; คำสั่งซื้อเกิดขึ้นเฉพาะหลังจากยืนยันตัวเลือกแล้ว
- **เหตุผล**: ป้องกันสถานะ "คำสั่งซื้อที่ยังไม่ได้เลือกตัวเลือก" ซึ่งเป็นสถานะที่ไม่สมบูรณ์; สอดคล้องกับธรรมชาติทางธุรกิจ

## ความสัพันธ์ระหว่าง Context ที่เป็นไปได้ (สำหรับ `ddd-context-map` ไปละเอียดต่อ)

- Booking ← Handling: ต้นน้ำ-ปลายน้ำ; Handling เป็นแหล่งข้อเท็จจริงต้นน้ำ Booking เป็นผู้บริโภค
- Booking → Tracking: ต้นน้ำ-ปลายน้ำ; Booking เผยแพร่ผลลัพธ์ที่คำนวณได้ Tracking สมัครรับและ project
- Handling → Tracking: ทางอ้อม (ผ่าน Booking) Tracking ไม่อ่าน Handling โดยตรง
- Booking ↔ Pathfinder: Customer-Supplier + ACL, Booking เป็นลูกค้า Pathfinder เป็นผู้ให้บริการ
