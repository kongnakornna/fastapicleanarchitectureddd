# 00 — Blind Run Fuzzy Prompt

> โปรด prompt นี้ใช้สำหรับ blind run: จำลองความต้องการที่คลุมเครือจากฝั่งธุรกิจจริง **ไม่ประกอบด้วยศัพท์ DDD ใดๆ** (Aggregate, Context, Entity, Value Object, Event Storming, Ubiquitous Language ฯลฯ ต้องไม่ปรากฏ); **ไม่ประกอบด้วยชื่อคลาส/ชื่อแพ็กเกจในโค้ดตัวอย่าง** (Cargo, HandlingEvent, Itinerary, Voyage, RouteSpecification, Pathfinder ฯลฯ ต้องไม่ปรากฏ)

## ภูมิหลังทางธุรกิจ (จากบันทึกการประชุมเบื้องต้นของบริษัทโลจิสติกส์ระหว่างประเทศแห่งหนึ่ง)

เราเป็นผู้ให้บริการโลจิสติกส์ทางทะเลระหว่างประเทศ ลูกค้าหลักคือภาคการผลิตและบริษัทการค้าต่างประเทศ ในช่วงไม่กี่ปีที่ผ่านมามีปริมาณงานเพิ่มขึ้นเป็นเท่าตัว กระบวนการเดิมที่อาศัยอีเมล + Excel + ระบบกระจัดกระจายจำนวนหนึ่งตามไม่ทัน ทำให้มีลูกค้าร้องเรียนและความขัดแย้งภายในเพิ่มขึ้น เราต้องการสร้างระบบใหม่ขึ้นมา เพื่อเชื่อมโยงกระบวนการทั้งหมดตั้งแต่ "ลูกค้าแจ้งความต้องการขนส่ง" ไปจนถึง "ส่งมอบสินค้าและลูกค้าเซ็นรับ" เข้าด้วยกัน

## ปัญหาในปัจจุบัน

1. **ขั้นตอนการรับคำสั่งซื้อของลูกค้า**: โดยปกติลูกค้าจะบอกเราแค่จุดเริ่มต้น ปลายทาง และเวลาถึงล่าสุด เจ้าหน้าที่จองระวางของเราต้องเข้าไปค้นหน้าบริษัทเรือหลายๆ แห่งด้วยตนเองว่ามีเรือไหนบ้างที่จะไปได้ ออกท่าเมื่อไหร่ ต้องถ่ายลำหรือไม่ แล้วจึงตอบกลับลูกค้าด้วยทางเลือกที่เป็นไปได้หลายแบบ เมื่อลูกค้าเลือกแบบใดแบบหนึ่งแล้วเราจึงนับว่าลงคำสั่งซื้อสำเร็จ การติดต่อสื่อสารไปมานี้โดยเฉลี่ยใช้เวลา 2~3 วัน ลูกค้าบ่นว่าช้า
2. **การลงทะเบียนปฏิบัติการท่าเรือ**: หลังจากสินค้าออกจากคลังแล้วจะผ่านท่าเรือหลายแห่ง ได้แก่ รับของ ขึ้นเรือ ระหว่างทาง ลงเรือ ถ่ายลำ ถึงท่าเรือปลายทาง ลูกค้ามารับของ บุคลากรปฏิบัติการของแต่ละท่าเรือ (อาจเป็นคนของเราเองหรือพันธมิตรภายนอก) จะลงทะเบียนลงในระบบว่า "เมื่อไหร่ ที่ท่าเรือไหน เกิดอะไรขึ้น" ปัจจุบันข้อมูลการลงทะเบียนเหล่านี้ยุ่งเหยิงมาก: บางอันถูกส่งซ้ำซ้อน บางอันกรอกฟิลด์ไม่ถูกต้องตามมาตรฐาน บางอันล่าช้าเข้ามาหลายวัน
3. **การระบุความผิดปกติ**: บางครั้งสินค้าถูกลงผิดท่าเรือ (เช่น ควรจะเป็น New York แต่ดันลงที่ Tokyo) ปัจจุบันเราพบปัญหาประเภทนี้ได้ก็ต่อเมื่อลูกค้าโทรมาบ่น ระบบเองตรวจไม่เจอ เมื่อเกิดข้อผิดพลาด เราจำเป็นต้องวางแผนใหม่จากตำแหน่งปัจจุบันไปยังปลายทาง และพยายามรักษาเวลามาถึงตามสัญญาเดิมของลูกค้าไว้ให้มากที่สุด
4. **ประสบการณ์การสอบถามของลูกค้า**: ลูกค้าต้องการรู้ว่า "ตอนนี้สินค้าของฉันอยู่ที่ไหน? ต่อไปต้องทำอะไร? คาดว่าจะถึงเมื่อไหร่? ไปผิดทางไหม?" ตอนนี้ทำได้แค่โทรถามเจ้าหน้าที่บริการลูกค้า แล้วเจ้าหน้าที่ก็เข้าไปค้นจากระบบต่างๆ มาเรียบเรียงคำตอบให้
5. **การวางแผนเส้นทาง**: งานหาเที่ยวเรือและต่อเลกการเดินเรือ ตอนนี้เราใช้ระบบออนไลน์ที่พันธมิตรภายนอกจัดหาให้ (เป็นบริษัทที่เชี่ยวชาญด้านข้อมูลเส้นทางเดินเรือโดยเฉพาะ ไม่ใช่เราพัฒนาเอง) เราเรียกใช้ API ของพวกเขา แล้วพวกเขาส่งผลลัพธ์ที่ทำได้หลายแบบมาให้ ความสัมพันธ์นี้จะคงอยู่ต่อไปในอนาคต เราไม่ได้ตั้งใจจะสร้างข้อมูลเส้นทางเดินเรือเอง

## เป้าหมายที่คาดหวัง

- ลูกค้าสามารถส่งความต้องการขนส่งออนไลน์ได้ (จุดเริ่มต้น ปลายทาง เวลาถึงล่าสุด) ระบบส่งรายการทางเลือกที่ทำได้จริงกลับมา เมื่อลูกค้าเลือกแบบใดแบบหนึ่งก็ถือว่าลงคำสั่งซื้อสำเร็จ
- ฝ่ายปฏิบัติการท่าเรือสามารถลงทะเบียนข้อเท็จจริงการปฏิบัติการผ่าน Web/API/การนำเข้าไฟล์ เป็นต้น; ระบบต้องสามารถระบุการส่งซ้ำซ้อนและข้อมูลที่ไม่ถูกต้องได้
- ระบบระบุสถานการณ์ "ไปผิดทาง" อัตโนมัติ และแจ้งผู้เกี่ยวข้อง รวมถึงสนับสนุนการวางแผนเส้นทางใหม่
- ลูกค้าสามารถสอบถามตำแหน่ง สถานะ ขั้นตอนที่คาดว่าจะทำต่อไป และเวลาถึงโดยประมาณของสินค้าตนเองบนเว็บไซต์ได้แบบเรียลไทม์
- รักษา coupling แบบหลวมกับผู้ให้ข้อมูลเส้นทางเดินเรือภายนอก ไม่อนุญาตให้การเปลี่ยนแปลงของพวกเขาเจาะระบบหลักของเราแบบง่ายๆ

## สิ่งที่ไม่ใช่เป้าหมาย (ลูกค้าระบุชัดเจนว่าไม่ทำในรุ่นนี้)

- **ไม่ทำการเรียกเก็บเงินและการเงิน**: เส้นทางนี้คิดราคาเท่าไหร่ ควรได้รับเท่าไหร่ ออกใบแจ้งหนี้ กระทบยอด เหล่านี้ยังไม่ทำตอนนี้ เก็บไว้รุ่นถัดไป
- **ไม่ทำ CRM ลูกค้า**: ข้อมูลติดต่อของลูกค้า แฟ้มเครดิต ประวัติการกระทบยอด ไม่อยู่ในขอบเขตของระบบนี้
- **ไม่ทำการจัดตารางภายในของบริษัทเรือ**: เราไม่จัดตารางเที่ยวเรือให้บริษัทเรือ
- **ไม่ทำการจัดการคลังสินค้า**: สินค้าในคลังวางอย่างไร นับสต็อกอย่างไร ไม่อยู่ในระบบนี้

## ข้อจำกัด

- ระบบต้องสามารถรับข้อมูลปฏิบัติการท่าเรือภายนอกแบบ asynchronous ได้: ฝ่ายตรงข้ามอาจล่าช้าจากหลายชั่วโมงถึงหลายวันกว่าจะผลักดัน Event เข้ามา; ฝ่ายเราต้องสามารถตัดรายการซ้ำซ้อนได้ตอนรับเข้า
- อินเทอร์เฟซกับผู้ให้ข้อมูลเส้นทางเดินเรือภายนอกอาจเปลี่ยนแปลงได้ทุกเมื่อ ฝ่ายเราไม่อนุญาตให้ฟิลด์ของพวกเขาปรากฏโดยตรงในโมเดลหลักของเรา
- สินค้าหนึ่งรายการตั้งแต่สั่งจนกว่าจะส่งมอบโดยปกติกินเวลา 2~6 สัปดาห์ ในระหว่างนั้นอาจมีการเปลี่ยนปลายทาง เปลี่ยนเส้นทาง หรือเกิดความผิดปกติได้
- ขนาดการปฏิบัติการ: ที่พีคมีการสั่ง 5000 รายการต่อวัน, Event การปฏิบัติการ 500,000 รายการ; QPS ที่พีคประมาณ 200
- ทีม: ทีมจองระวาง/บริการลูกค้า, ทีมเชื่อมต่อข้อมูลปฏิบัติการท่าเรือ, ทีม frontend ฝั่งลูกค้า มีความเป็นอิสระค่อนข้างสูงต่อกัน

## สิ่งที่เราคาดหวังให้คุณช่วยทำ

ช่วยเราปรับเปลี่ยนความต้องการทางธุรกิจที่คลุมเครือชุดนี้ให้กลายเป็น input การสร้างโมเดลที่ชัดเจน: ปัญหาที่แท้จริงคืออะไร ขอบเขตอยู่ตรงไหน แนวคิดหลักมีอะไรบ้าง ความเสี่ยงทางธุรกิจหลักคืออะไร และข้อมูลจำเป็นใดบ้างที่ต้องใช้เพื่อก้าวสู่การสร้างโมเดลขั้นถัดไป
