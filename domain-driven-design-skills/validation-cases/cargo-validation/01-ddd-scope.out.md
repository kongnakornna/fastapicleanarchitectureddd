# 01 — ผลลัพธ์ ddd-scope (Blind Run)

> ข้อมูลนำเข้า: `00-fuzzy-prompt.md` (ไม่มีคำศัพท์ DDD ไม่มีชื่อคลาสตัวอย่าง)
> ไฟล์นี้เป็นผลลัพธ์จากการจำลองการทำงานของ `ddd-scope` ใน blind run โดย **ไม่ได้อ้างอิง** วัสดุ ground truth ใน `reference/` ใดๆ

## การระบุปัญหาและคุณค่า

- **การระบุปัญหา**: กระบวนการขนส่งทางทะเลระหว่างประเทศที่มีอยู่เดิม "อีเมล + Excel + ระบบกระจัดกระจาย" ทำให้การทำงานร่วมกันแบบ end-to-end จากการรับคำขอขนส่งของลูกค้าไปจนถึงการรับมอบสินค้าไม่สามารถติดตาม ตรวจสอบ และแทรกแซงได้ ส่งผลให้รอบการสั่งซื้อยาวนาน ข้อมูลการปฏิบัติงานยุ่งเหยิง การระบุความผิดปกติล่าช้า และการสอบถามด้วยตนเองของลูกค้าขาดหายไป
- **การระบุคุณค่า**: สร้างระบบเดียวที่มีศูนย์กลางอยู่ที่ "วงจรชีวิตทั้งหมดของการขนส่งหนึ่งรายการ" ทำให้การจอง การปฏิบัติงานที่ท่าเรือ การวางแผนใหม่กรณีผิดปกติ และการสอบถามของลูกค้าทำงานร่วมกันบนฐานข้อเท็จจริงเดียวกัน ลดเวลาตอบสนองการสั่งซื้อลงอย่างมีนัยสำคัญ และเปลี่ยนความผิดปกติจาก "ลูกค้าโทรมาเปิดเผย" เป็น "ระบบระบุได้เอง"

## เป้าหมาย / เป้าหมายที่ไม่ใช่

### เป้าหมาย

1. ลูกค้าส่งคำขอขนส่งออนไลน์ (จุดเริ่มต้น จุดหมาย เวลาถึงล่าสุด) ระบบส่งรายการตัวเลือกที่เป็นไปได้กลับมา ลูกค้าเลือกแล้วถือว่าการสั่งซื้อสำเร็จ
2. ผู้ปฏิบัติงานที่ท่าเรือลงทะเบียนข้อเท็จจริงการปฏิบัติงานผ่านหลายช่องทาง Web/API/ไฟล์ได้ ระบบสามารถระบุการส่งซ้ำและข้อมูลผิดกฎหมายได้โดยอัตโนมัติ
3. ระบุความผิดปกติ "สินค้าไปผิดทาง" ได้เอง และสนับสนุนการวางแผนเส้นทางใหม่ไปยังจุดหมายจากตำแหน่งปัจจุบัน โดยให้ความสำคัญกับการรักษาเวลาถึงที่สัญญาไว้
4. ลูกค้าสามารถสอบถามตำแหน่งปัจจุบัน สถานะ การกระทำที่คาดหวังในขั้นตอนถัดไป และเวลาถึงโดยประมาณของสินค้าด้วยตนเอง
5. รักษาความสัมพันธ์แบบหลวมกับผู้ให้ข้อมูลเส้นทางเดินเรือภายนอก: ฟิลด์ภายนอกไม่ปรากฏโดยตรงในโมเดลหลัก การเปลี่ยนแปลงจากภายนอกไม่เจาะทะลุกระบวนการหลัก

### เป้าหมายที่ไม่ใช่ (ระบุอย่างชัดเจนว่าไม่ทำ)

- **ไม่ทำการเรียกเก็บเงินและการเงิน**: การกำหนดราคา ลูกหนี้ การออกใบแจ้งหนี้ การกระทบยอด อยู่นอกขอบเขตรุ่นนี้
- **ไม่ทำ CRM ลูกค้า**: ข้อมูลติดต่อ แฟ้มเครดิต ประวัติการกระทบยอดของลูกค้า ไม่รวมอยู่ในระบบนี้
- **ไม่ทำการจัดตารางภายในของบริษัทเรือ**: ไม่จัดตารางเที่ยวเรือให้บริษัทเรือ
- **ไม่ทำการจัดการคลังสินค้า**: การจัดวางและตรวจนับสินค้าในคลัง ไม่รวมอยู่ในระบบนี้

| **ธุรกิจ**: เป้าหมายที่ไม่ใช่ถูกฝ่าฝืนโดยนัย (เช่น frontend ต้องการดูราคา) | ขอบเขตขยายเกิน ทีมถูกบังคับปฏิเสธ | คำขอชั่วคราวจากลูกค้า/frontend | ใส่เป้าหมายที่ไม่ใช่เข้าไปในการลงนามรับมอบ; คำขอที่เกินขอบเขตต้องผ่านการตรวจสอบการเปลี่ยนแปลง |
| **การบูรณาการ**: อินเทอร์เฟซของผู้ให้ข้อมูลเส้นทางภายนอกเปลี่ยนแปลง | การสั่งซื้อและการวางแผนใหม่ใช้ไม่ได้ | อีกฝ่ายอัปเกรดเวอร์ชันหรือเปลี่ยนชื่อฟิลด์ | ชั้นป้องกันการกัดกร่อน; การทดสอบสัญญา; ลดระดับอัตโนมัติ |
| **การบูรณาการ**: ข้อมูลปฏิบัติงานที่ท่าเรือมาสาย ซ้ำ ฟิลด์ไม่ได้มาตรฐาน | การสอบถามลูกค้าไม่แม่นยำ การแจ้งเตือนผิดปกติผิด | ฝ่ายภายนอกส่งผ่านอีเมล/ไฟล์/async push | การดูดซับแบบ async + คีย์ตัดซ้ำ + การตรวจสอบล้มเหลวเข้าเขตกักกัน |
| **ความสอดคล้อง**: "เวลาเกิดจริง" กับ "เวลาถึงระบบ" ของการลงทะเบียนข้อเท็จจริงปฏิบัติงานไม่ตรงกัน | การคำนวณสถานะผิดพลาด | ฝ่ายภายนอกล่าช้าหลายชั่วโมงถึงหลายวัน | ใช้ "เวลาเกิดจริง" ขับเคลื่อนการคำนวณสถานะ; "เวลาถึงระบบ" ใช้สำหรับการตรวจสอบเท่านั้น |
| **ความสอดคล้อง**: สถานะสินค้าคำนวณจากข้อมูลหลายแหล่ง เกณฑ์ตัดสินไม่เป็นมาตรฐานเดียว | "สินค้าอยู่ที่ไหน" มาตรฐานฝ่ายบริการลูกค้ากับระบบไม่ตรงกัน | มีหลายระบบใช้งานพร้อมกัน | กำหนดกฎการคำนวณที่เชื่อถือได้; ห้ามให้สถานะถูกเขียนทับจากภายนอกโดยตรง |
| **ความสอดคล้อง**: การระบุความผิดปกติล่าช้า | ลูกรับรู้ถึงข้อผิดพลาดแล้ว ระบบค่อยแจ้งเตือน | ขนถ่ายผิด โหลดผิด มาถึงสาย | ผูกการระบุความผิดปกติกับการประมวลผลทันทีของ Event การลงทะเบียนปฏิบัติงาน |
| **การส่งมอบ**: 500,000 Event/วันที่พีค การตัดสินซ้ำและการคำนวณสถานะมีต้นทุนสูง | การลงทะเบียนเข้าระบบล่าช้า การสอบถามของลูกค้าช้า | ช่วงเวลาที่พีค | Async + Partition; เขียน idempotent ก่อน แล้วคำนวณมุม-view ทีหลัง |
| **การส่งมอบ**: สามทีมจังหวะอิสระ การเชื่อมต่ออินเทอร์เฟซทำซ้ำหลายครั้ง | ตารางล่าช้า | การพัฒนาคู่ขนานไม่ล็อกสัญญา | ล็อกขอบเขตและสัญญาให้เร็วที่สุด; การทดสอบสัญญาที่ milestone |
| **การส่งมอบ**: ความคาดหวังประสบการณ์การสั่งซื้อสูงเกินไป (ส่งตัวเลือกกลับมาภายในวินาที) | ไม่ถึงความคาดหวังทำให้อัตราการซื้อซ้ำลดลง | ผู้ให้ข้อมูลภายนอกตอบสนองช้า | ระบุชัดเจนว่าการค้นหาตัวเลือกเป็น "เกือบเรียลไทม์"; อนุญาตให้ลดระดับและเก็บแคช |

(ครอบคลุมสี่ประเภท: ธุรกิจ / การบูรณาการ / ความสอดคล้อง / การส่งมอบ)

## รายการเตรียมความพร้อมขั้นตอนถัดไป

ข้อมูลและบทบาทขั้นต่ำที่ต้องการเพื่อเข้าสู่ `ddd-discover`:

- [ ] **บทบาท**: เจ้าหน้าที่จอง ตัวแทนผู้ปฏิบัติงานที่ท่าเรือ (รวมตัวอย่างพันธมิตรภายนอก) ตัวแทนฝ่ายบริการลูกค้า ผู้จัดการฝ่ายผลิตภัณฑ์ frontend สำหรับลูกค้า ผู้รับผิดชอบการบูรณาการกับผู้ให้ข้อมูลเส้นทางภายนอก
- [ ] **ข้อมูลนำเข้าที่จำเป็น**:
  - ตัวอย่าง "การขนส่งปกติหนึ่งรายการ" ที่สมบูรณ์อย่างน้อย 1 ตัวอย่าง (รวมการสั่งซื้อ การลงทะเบียนปฏิบัติงานแต่ละท่าเรือ การจัดส่ง)
  - ตัวอย่างความผิดปกติอย่างน้อย 2 ตัวอย่าง: ขนถ่ายผิด + การวางแผนใหม่ การลงทะเบียนปฏิบัติงานล่าช้า/ซ้ำ
  - ตัวอย่างสัญญาอินเทอร์เฟซที่มีอยู่ของผู้ให้ข้อมูลเส้นทางภายนอก (ไม่ดูการ implement ดูเฉพาะฟิลด์)
  - รายการประเภทข้อเท็จจริงการปฏิบัติงานที่เป็นไปได้และเงื่อนไขธุรกิจล่วงหน้า (เช่น "ขึ้นเรือ" ต้องเกิดหลัง "รับของ")
- [ ] **ผลลัพธ์ที่คาดหวัง**: ตาราง Event Flow (เส้นทางหลัก + การขนถ่ายผิดวางแผนใหม่ + ข้อมูลมาสายสองเส้นทางผิดปกติ) ผู้สมัครคำสั่ง ผู้สมัคร Event จุดร้อน (ความสอดคล้อง / การบูรณาการ / ประสิทธิภาพ / การปฏิบัติตามกฎระเบียบ) รายการคลุมเครือ เบาะแสขอบเขต (กลุ่มผู้สมัครความสามารถที่แบ่งจากสามทีม)
