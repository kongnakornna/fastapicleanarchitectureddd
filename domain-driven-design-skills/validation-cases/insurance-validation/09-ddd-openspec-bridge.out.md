# 09 — ผลผลิต ddd-openspec-bridge (Blind Run)

> อินพุต: `01-ddd-scope.out.md` + `03-ddd-subdomains.out.md` + `04-ddd-contexts.out.md` + `05-ddd-context-map.out.md` + `06-ddd-aggregates.out.md` + `07-ddd-domain-interactions.out.md` (+ 08 ประเมินตนเองเป็นอินพุตทางเลือก)
> มาตรฐานการทำงาน: นิยามใน `docs/ddd-openspec-mapping.md`
> ไฟล์นี้เป็นผลลัพธ์การจำลองการทำงานของ `ddd-openspec-bridge` ใน blind run แปลงแบบจำลองการรับประกันภัยและการเรียกร้องค่าสินไหมเป็นชุดการเปลี่ยนแปลง OpenSpec

---

## ชุดการเปลี่ยนแปลง: `digital-claims-pipeline`

> ขอบเขตการครอบคลุม: การตัดสินใจรับประกันภัย (Core) → การประเมินค่าเสียหายและจ่าย (Core) → การดำเนินการจ่าย (Generic อ้างอิง) การรับประกันภัยเสนอราคาและจัดการกรมธรรม์เป็น Bounded Context ที่เกี่ยวข้อง ชุดการเปลี่ยนแปลงนี้เกี่ยวข้องเฉพาะฝั่งที่ใช้สัญญา ไม่เขียนมาตรฐานใหม่

## 1. การตั้งค่าทั่วไป `openspec/config.yaml` (ประกาศครั้งเดียว ดูแลโดยขั้นตอน `ddd-contexts`)

```yaml
context: |
  ## การแมปโดเมนของโครงการ
  บริบทการจัดการกรมธรรม์ (Policy Context)
 - บริบทการเคลม (Claim Context)
 - บริบทการชำระเงิน (Payment Context)
 - บริบทฝ่ายลูกค้า (Party Context)
 - บริบทการเสนอราคา (Quotation Context)
 - บริบทมุมมองด้านกฎระเบียบ (Regulatory Context)

  ## สแต็กเทคโนโลยีและข้อจำกัดด้านสถาปัตยกรรม
  - รูปแบบสถาปัตยกรรม: ขับเคลื่อนด้วยเหตุการณ์ + สถาปัตยกรรมแบบแบ่งชั้น (Domain / Application / Infrastructure)
  - กฎ: การเปลี่ยนแปลง Aggregate ทั้งหมดต้องขับเคลื่อนความสอดคล้องในที่สุดผ่านเหตุการณ์โดเมน; หนึ่งทรานแซกชันแก้ไขเพียงหนึ่ง Aggregate เท่านั้น
  - การรวมระบบ: ระบบอัตราและระบบเงินทุนภายนอกเชื่อมต่อผ่าน ACL; เหตุการณ์ข้ามบริบทใช้รูปแบบ Outbox
```

## 2. เมตาดาต้าชุดการเปลี่ยนแปลง `changes/digital-claims-pipeline/.openspec.yaml`

```yaml
name: digital-claims-pipeline
created: 2026-08-05
status: proposed

  - underwriting-context/underwriting-decision

  - payment-context/payment-execution
```

## 3. `proposal.md`

### เหตุผล

ข้อมูลขาดความต่อเนื่องในกระบวนการรับประกันภัยและการเรียกร้องค่าสินไหมทดแทน: ผู้รับประกันภัยไม่เห็นประวัติผลงานเรียกร้องค่าสินไหมทดแทนที่สมบูรณ์ พนักงานเรียกร้องค่าสินไหมทดแทนไม่ได้รับข้อมูลเงื่อนไขที่แม่นยำ ฝ่ายบริหารไม่สามารถติดตามขนาดเรียกร้องค่าสินไหมรอตัดบัญชีแบบเรียลไทม์ ส่งผลให้การตัดสินใจช้า ข้อผิดพลาดมาก และการส่งข้อมูลกำกับดูแลเป็นไปอย่างล่าช้า

### สิ่งที่เปลี่ยนแปลง

- ใน Bounded Context การตัดสินใจรับประกันภัย เพิ่มความสามารถ: การตัดสินใจรับประกันภัย (UnderwritingDecision) — รับ/เพิ่มเบี้ย/จำกัดความรับผิดชอบ/ปฏิเสธ รวมการประเมินการประกันต่อ **Subdomain Core ทำ Scenario ทั้งหมด**
- ใน Bounded Context เรียกร้องค่าสินไหม เพิ่มความสามารถ: การประเมินค่าเสียหาย (LossAssessment) — ประเมินค่าเสียหาย ระงับสอบสวน อนุมัติ ปิดคดี **Subdomain Core ทำ Scenario ทั้งหมด**
- ใน Bounded Context การจ่าย เพิ่มความสามารถ: การดำเนินการจ่าย (PaymentExecution) — รับคำสั่ง ดำเนินการแบบemsp;font ใบเสร็จ **Subdomain Generic** อ้างอิงสัญญาจ่ายที่มีอยู่
- 引入 Domain Event: `UnderwritingDecisionMade`, `PaymentRequested`, `PaymentExecuted`, `ClaimClosed` (ตามนิยามในสารบัญเหตุการณ์ 07)
- ภาษาทั่วไป: กรณีรับประกันภัย การตัดสินใจรับประกันภัย แจ้งเหตุ การประเมินค่าเสียหาย ระงับสอบสวน คำสั่งจ่าย ใบเสร็จการจ่าย (ทั้งหมดอยู่ในคำศัพท์ `ddd-contexts`)

### ผลกระทบ

- **Capabilities**: `underwriting-context/underwriting-decision`, `claim-context/loss-assessment`, `payment-context/payment-execution`
- การเปลี่ยนแปลง Aggregate:
  - Aggregate UnderwritingCase: เพิ่มการตัดสินใจและการประเมินการประกันต่อ (ไม่ทำลาย)
  - Aggregate Claim: เพิ่มสถานะเครื่องจักรระงับสอบสวนและขอบเขตสะสมจ่าย (I-5 / I-6)
  - Aggregate PaymentInstruction: เพ่ิมการรับคำสั่งและใบเสร็จ (คีย์emsp;fontเปลี่ยนแปลงไม่ได้)

### เป้าหมาย

- การตัดสินใจรับประกันภัย → อัตราออกกรมธรรม์สังเกตได้ (อัตราครบถ้วนบันทึกการตัดสินใจ 100%)
- ผลการประเมินค่าเสียหายคำนวณแม่นยำ (ค่า deductible/ข้อยกเว้น/วงเงินสะสมตรวจสอบอัตโนมัติ เปลี่ยนจำนวนด้วยมือถูกปฏิเสธ)
- อัตราปฏิเสธจ่ายระหว่างระงับสอบสวน 100% (สถานะเครื่องจักรแยกกัน ไม่ใช่วินัยบุคคล)
- อัตราความสำเร็จจ่าย ≥ 99.9% จ่ายซ้ำ 0 รายการ (คีย์emsp;fontรับประกัน)

## 4. `design.md`

### 4.1 การแปลงสถาปัตยกรรมชั้น

| ชั้น              | เนื้อหา                                                                                 | ที่มา                                         |
| :--------------- | :-------------------------------------------------------------------------------------- | :------------------------------------------- |
| Domain           | Aggregate (UnderwritingCase / Claim / PaymentInstruction) Invariant Domain Event       | `ddd-aggregates` + `ddd-domain-interactions` |
| Application      | การจัดลำดับ Domain Service (UnderwritingService / LossAssessmentService / PaymentGateway) ขั้นตอนอนุมัติ | `ddd-domain-interactions`                    |
| Infrastructure   | การใช้งาน Repository Event Bus (Outbox) ACL Adapter (อัตรา/ระบบการเงิน)                  | `ddd-context-map`                            |

### 4.2 การแปลงแบบจำลองข้อมูล

| Aggregate           | ขอบเขตเก็บถาวร                              | สถานะสำคัญ                                                                     |
| :------------------ | :------------------------------------------ | :----------------------------------------------------------------------------- |
| UnderwritingCase    | caseId เป็นคีย์หลัก; สืบทอดการตัดสินใจด้วยเหตุการณ์ | กำลังรับประกันภัย → ตัดสินใจแล้ว                                              |
| Claim               | claimId เป็นคีย์หลัก; บันทึกประเมินค่าเสียหายแบบเพิ่มต่อเนื่อง | แจ้งเหตุแล้ว → กำลังประเมินค่าเสียหาย → ระงับ (สอบสวน) / อนุมัติแล้ว → จ่ายแล้ว → ปิดคดี |
| PaymentInstruction  | instructionId เป็นคีย์หลัก + claimId คีย์emsp;font | รอดำเนินการ → ดำเนินการแล้ว / ล้มเหลวลองใหม่                                |

### 4.3 ข้อมูลหลัก (ลำดับเหตุการณ์)

### 4.4 แบบอย่างขับเคลื่อนด้วยเหตุการณ์ (เทียบแผนที่คำแนะนำ ภาคผนวก A)

- **เผยแพร่**: ความสอดคล้องข้าม Aggregate และการเชื่อมต่อข้าม Bounded Context ใช้เหตุการณ์ทั้งหมด `PaymentRequested` เขียน Outbox ในธุรกรรม Claim เผยแพร่หลังธุรกรรม提交
- **ผู้ใช้**: ฝั่งผู้ใช้ `PaymentExecuted` ใช้ `paymentId + claimId` เป็นคีย์emsp;font เก็บถาวรตัดซ้ำ ล้มเหลวเข้าคิวลองใหม่ ห้ามย้อนกลับ Aggregate ต้นน้ำ
- **ชดเชย**: จ่ายล้มเหลว (ลองใหม่ได้) ลองใหม่อัตโนมัติ ≤3 ครั้ง ลองไม่ได้ส่งช่องทางคน ปิดคดีต้องจ่ายสำเร็จก่อน
- **แปล**: ใบเสร็จระบบการเงินภายนอกผ่าน ACL-3 แปลเป็น `PaymentExecuted` ภายใน อัตราผ่าน ACL-1 แปลเป็น `QuoteTerms`

### 4.5 พิธีสาร API (ชุดการเปลี่ยนแปลงนี้เกี่ยวข้อง)

| API / สัญญา                     | ทิศทาง                     | พิธีสาร          | คีย์emsp;font                  |
| :------------------------------ | :------------------------- | :--------------- | :------------------------------- |
| UnderwritingDecisionMade        | Underwriting → Policy      | เหตุการณ์ (Outbox) | caseId + decisionVersion         |
| PaymentRequested                | Claim → Payment            | เหตุการณ์ (Outbox) | instructionId                    |
| PaymentExecuted                 | Payment → Claim            | เหตุการณ์ (Outbox) | paymentId + claimId              |
| ClaimClosed                     | Claim → Regulatory         | เหตุการณ์ (Outbox) | claimId                          |

## 5. สารบัญ `specs/` (จัดเรียงตาม Bounded Context)

### 5.1 `specs/underwriting-context/underwriting-decision/spec.md`

#### ข้อกำหนด: ความสามารถการตัดสินใจรับประกันภัย

ระบบควรสนับสนุนผู้รับประกันภัยในการตัดสินใจรับ บวกราคา จำกัดความรับผิดชอบ หรือปฏิเสธคำขอประกันภัย การตัดสินใจมีผลบังคับและออกกรมธรรม์แล้วเปลี่ยนแปลงไม่ได้; คำขอหนึ่งรายการมีการตัดสินใจที่มีผลบังคับได้ไม่เกินหนึ่งรายการ

##### Scenario: รับคำขอและกระตุ้นออกกรมธรรม์

- **Given** คำขอประกันภัย A ที่เสนอราคาแล้ว กับ กรณีรับประกันภัย C
- **When** ผู้รับประกันภัยตัดสินใจรับประกัน C
- **Then** สร้างการตัดสินใจรับประกัน D (decision = รับ)
- **And** เผยแพร่เหตุการณ์ UnderwritingDecisionMade พก caseId และ applicationId
- **And** การตัดสินใจ D เป็นการตัดสินใจที่มีผลบังคับ

##### Scenario: ปฏิเสธเปลี่ยนการตัดสินใจหลังออกกรมธรรม์

- **Given** การตัดสินใจ D มีผลบังคับแล้วและออกกรมธรรม์基于 D แล้ว
- **When** ผู้รับประกันภัยส่งการตัดสินใจ D' สำหรับคำขอเดียวกันอีกครั้ง
- **Then** ปฏิเสธการส่ง คืนข้อผิดพลาดการตัดสินใจเปลี่ยนแปลงไม่ได้
- **And** ไม่เผยแพร่เหตุการณ์ใดๆ

##### Scenario: วัตถุเอาประกันความเสี่ยงสูงกระตุ้นประเมินการประกันต่อ

- **Given** วัตถุเอาประกันของคำขอประกันภัย A เกินจำนวนกันความเสี่ยงของตนเอง
- **When** ผู้รับประกันภัยเริ่มรับประกันภัย
- **Then** บันทึกความต้องการประกันต่อ R (สัดส่วนต้องประกันต่อ)
- **And** ผลประกันต่อรวมเป็นฐานการตัดสินใจแล้วตัดสินใจ

> ตรงกับ Invariant I-3 ของ `ddd-aggregates`; ไม่ได้แทรกซึมรายละเอียดฐานข้อมูล/HTTP/ORM

### 5.2 `specs/claim-context/loss-assessment/spec.md`

#### ข้อกำหนด: ความสามารถประเมินค่าเสียหายและจ่าย

ระบบควรคำนวณจำนวนเงินที่ต้องจ่ายตามผลการตรวจสอบและสแน็ปช็อตเงื่อนไขขณะแจ้งเหตุ (ค่า deductible ข้อยกเว้น วงเงินสะสมตรวจสอบอัตโนมัติ) สนับสนุนการระงับสอบสวนแยกกันและการอนุมัติหลายขั้น จำนวนเงินจ่ายเปลี่ยนแปลงด้วยมือไม่ได้

##### Scenario: ประเมินค่าเสียหายปกติและจ่ายตามสูตร

- **Given** แจ้งเหตุ CL เชื่อมกรมธรรม์แล้วถือสแน็ปช็อตเงื่อนไข S (ค่า deductible 2,000)
- **When** การตรวจสอบเสร็จสิ้น จำนวนค่าเสียหายที่ประเมิน 12,000
- **Then** คำนวณจำนวนต้องจ่าย = 12,000 - 2,000 = 10,000
- **And** สร้างผลการประเมินค่าเสียหาย L (金额 10,000 เปลี่ยนแปลงไม่ได้)
- **And** เผยแพร่เหตุการณ์ LossAssessed

##### Scenario: ปฏิเสธการอนุมัติจ่ายระหว่างระงับสอบสวน

- **Given** แจ้งเหตุ CL อยู่ในสถานะระงับสอบสวน
- **When** ผู้อนุมัติเริ่มการอนุมัติจ่ายสำหรับ CL
- **Then** ปฏิเสธการอนุมัติ คืนเหตุผลการระงับ
- **And** ไม่สร้างคำสั่งจ่าย

##### Scenario: จ่ายค่าสินไหมสะสมเกินวงเงินประกันปฏิเสธจ่ายใหม่

- **Given** แจ้งเหตุ CL จ่ายสะสมแล้ว 90,000 วงเงินประกัน 100,000
- **When** ผลประเมินค่าเสียหายใหม่จำนวนต้องจ่าย 20,000
- **Then** ปฏิเสธผลประเมินค่าเสียหายนี้ (10,000 + 20,000 > 100,000 ตามข้อจำกัดวงเงิน)
- **And** แจ้งเหตุเกินวงเงิน

##### Scenario: เอกสารมาช้าเข้าสู่สถานะรอเติมเต็ม

- **Given** แจ้งเหตุ CL ขาดเอกสารตรวจสอบ
- **When** พนักงานเรียกร้องค่าสินไหมระบุเอกสารขาดหาย
- **Then** แจ้งเหตุเข้าสู่สถานะรอเติมเต็ม
- **And** เผยแพร่เหตุการณ์ ClaimPendingInformation

##### Scenario: ความสูญเสียเดียวกันแจ้งเหตุซ้ำรวมกัน

- **Given** แจ้งเหตุ CL-1 มีอยู่แล้วยังไม่ปิดคดี
- **When** วัตถุเอาประกันเดียวกันช่วงเวลาเกิดเหตุเดียวกันได้รับแจ้งเหตุซ้ำ CL-2
- **Then** CL-2 รวมเข้า CL-1 คืนเลขแจ้งเหตุหลัก
- **And** เผยแพร่เหตุการณ์ DuplicateClaimMerged

> ตรงกับ Invariant I-5 / I-6 / I-8 / I-9 ของ `ddd-aggregates`; รวม 5 Scenario ผ่านเกณฑ์ความละเอียดและไม่ข้าม Aggregate Root

### 5.3 `specs/payment-context/payment-execution/spec.md`

#### ข้อกำหนด: ความสามารถดำเนินการจ่าย

ระบบควรรับคำสั่งจ่ายจากเรียกร้องค่าสินไหม รับประกันด้วยคีย์emsp;fontว่าไม่จ่ายซ้ำ ผลการดำเนินการส่งกลับเป็นใบเสร็จสู่ Bounded Context เรียกร้องค่าสินไหม

##### Scenario: รับคำสั่งและดำเนินการสำเร็จ

- **Given** เรียกร้องค่าสินไหม CL อนุมัติผ่านแล้ว 金额 10,000
- **When** เรียกร้องค่าสินไหมเริ่มคำสั่งจ่าย P (instructionId เป็นหนึ่งเดียว)
- **Then** สร้างคำสั่งจ่าย P รอดำเนินการ
- **And** เผยแพร่เหตุการณ์ PaymentInstructionAccepted

##### Scenario: คำสั่งซ้ำemsp;fontลดทอน

- **Given** คำสั่งจ่าย P ดำเนินการสำเร็จแล้ว
- **When** คำสั่งที่มี instructionId เดียวกันมาถึงอีกครั้ง
- **Then** ไม่จ่ายซ้ำ คืนใบเสร็จที่มีอยู่
- **And** เผยแพร่เหตุการณ์ PaymentExecuted (ใบเสร็จเดียวกัน)

> Subdomain Generic ตามแผนที่คำแนะนำอ้างอิงสัญญาจ่ายที่มีอยู่ได้ คีย์emsp;fontเปลี่ยนแปลงไม่ได้

## การตัดสินกระตุ้นการทบทวน

- ไม่ได้กระตุ้นการทบทวนใดๆ: การเขียน Scenario ไม่พบความกำกวมตรรกะ Domain; ไม่มีรูปแบบการเชื่อมต่อที่แสดงไม่ได้; ไม่มีรายละเอียดเทคนิคแทรก; ไม่มีข้อกำหนดเกินละเอียด; คำศัพท์ทั้งหมดอยู่ในคำศัพท์
- **เส้นทางการทบทวนของ Skill นี้ (→ aggregates / domain-interactions / context-map / contexts) ในกรณีนี้เป็น "zero trigger"** — สอดคล้องกับการประเมินตนเอง 08 เมื่อผ่านเกณฑ์คุณภาพแบบจำลองแล้วขั้นตอน V เชื่อมต่ออย่างราบรื่น
