## คู่มือการจับคู่ DDD กับ OpenSpec: จากโมเดล Domain สู่ข้อกำหนดทางวิศวกรรม

> 🌐 Domain-Driven Design (DDD) หรือการออกแบบซอฟต์แวร์ที่ขับเคลื่อนด้วยโดเมน คือแนวทางและปรัชญาในการพัฒนาซอฟต์แวร์ที่มุ่งเน้นการสร้างแบบจำลอง (Model) ของโค้ดให้สอดคล้องกับ "โดเมนธุรกิจ" (Domain) หรือปัญหาทางธุรกิจนั้นๆ อย่างใกล้ชิดที่สุด

คู่มือนี้กำหนดเส้นทางการแปลงมาตรฐานจากผลลัพธ์ของ Domain-Driven Design (DDD) ไปสู่เวิร์กโฟลว์แบบ OpenSpec โดยการผสมผสานความเข้าใจเชิง domain ของ DDD เข้ากับพลังการปฏิบัติงานที่มีโครงสร้างของ OpenSpec เพื่อสร้างระบบเชื่อมต่อที่เชื่อถือได้สูงจากโมเดลสู่โค้ด

---

## 1. การจัดวางเชิงกลยุทธ์: ใช้ "Domain" จัดระเบียบ "Spec"

ในการออกแบบระบบขนาดใหญ่ การจัดวางเชิงกลยุทธ์เป็นกุญแจสำคัญในการรักษาความเรียบร้อยของสถาปัตยกรรม การนำวิธีการแบ่งพื้นที่ของ DDD มาใช้ในโครงสร้างไดเรกทอรีของ OpenSpec ทำให้เกิดการเชื่อมต่อระหว่างการออกแบบและข้อกำหนดอย่างเป็นธรรมชาติ

### 1.1 การจับคู่ Bounded Context กับไดเรกทอรี Domain

"Bounded Context" ของ DDD เป็นเครื่องมือหลักในการแบ่งขอบเขตฟังก์ชัน แต่ละขอบเขตมีโมเดล domain และ Ubiquitous Language ที่สอดคล้องกัน ใน OpenSpec สิ่งนี้ตรงกับไดเรกทอรีย่อยภายใต้ `specs/` วิธีการจัดวางนี้ทำให้มั่นใจว่าทุกขอบเขตธุรกิจที่ DDD ระบุไว้มีที่ชัดเจนในข้อกำหนดทางวิศวกรรม ป้องกันการแตกแยกของความรู้ด้าน domain

### 1.2 ภาพรวมทั้งหมดในไฟล์กำหนดค่า

โดยการประกาศความสัมพันธ์นี้ใน `openspec/config.yaml` สามารถให้บริบทสถาปัตยกรรมแก่ AI Agent ทำให้เข้าใจขอบเขตธุรกิจที่เกี่ยวข้องเมื่อจัดการกับการเปลี่ยนแปลงเฉพาะ

```yaml
# openspec/config.yaml ตัวอย่าง: การจับคู่ Domain กับ Bounded Context
context: |
  ## การแมปโดเมนของโครงการ
  ระบบนี้ยึดตามการออกแบบ DDD โดยมี Bounded Context หลัก ได้แก่:
  - บริบทการจัดการผู้ใช้ (User Context)
  - บริบทการจัดการคำสั่งซื้อ (Order Context)
  - บริบทการชำระเงิน (Payment Context)

  ## เทคโนโลยีและข้อจำกัดด้านสถาปัตยกรรม
  - รูปแบบสถาปัตยกรรม: สถาปัตยกรรมหกเหลี่ยม (Hexagonal)
  - แบ็กเอนด์: Java Spring Boot + MyBatis
  - กฎ: การเปลี่ยนแปลง Aggregate ทั้งหมดต้องขับเคลื่อนผ่านเหตุการณ์โดเมน (Domain Events) เพื่อให้เกิด final consistency
```

## 2. การลงมือเชิงยุทธวิธี: การดำเนินงาน DDD เชิงยุทธวิธี

การออกแบบเชิงยุทธวิธีกำหนดคุณภาพของการเขียนโค้ด OpenSpec มีวิธีการแสดงออกที่มีโครงสร้าง แปลงบล็อกโครงสร้างของ DDD เป็นลำดับงานที่ตรวจสอบได้และดำเนินการได้ โดยรองรับการพัฒนาแบบเพิ่มเติมผ่าน **กลไก Delta**

### 2.1 การจับคู่บล็อกโครงสร้างกับโครงสร้าง OpenSpec

เราแปลงผลลัพธ์ของ DDD เป็นส่วนประกอบหลักของ OpenSpec เพื่อขับเคลื่อน AI ให้ดำเนินการได้อย่างแม่นยำ

| โครงสร้าง OpenSpec             | ผลลัพธ์ DDD ที่สอดคล้อง                              | คำอธิบาย                                                         |
| :------------------------------ | :----------------------------------------------------- | :--------------------------------------------------------------- |
| **Domain**                      | **Bounded Context**                                    | ไดเรกทอรี domain หนึ่งตรงกับ Bounded Context หนึ่ง              |
| **Requirement**                 | **Domain Service** / **Command**                       | อธิบายฟังก์ชันหรือการดำเนินการหลักของธุรกิจ                     |
| **Scenario**                    | พฤติกรรมของ **Aggregate**                             | ใช้รูปแบบ **Given/When/Then (Gherkin)** อธิบายพฤติกรรม Aggregate อย่างแม่นยำ |
| **Design**                      | **Application Service**                                | ประสานงานหลาย Domain Service จัดการธุรกรรมและความปลอดภัย     |
| **Tasks**                       | รายการงานออกแบบเชิงยุทธวิธี                           | แปลงงานที่เฉพาะเจาะจง เช่น Entity, Value Object, Repository interface ให้เป็นงานที่ทำได้จริง |

> **ข้อตกลงป้องกันข้อผิดพลาด · ระดับของ Requirement**: Requirement แต่ละตัวควรโฟกัสไปที่**ความสามารถทางธุรกิจที่ตรวจสอบได้อิสระหนึ่งอย่าง** (มักตรงกับ Command หนึ่งตัวหรือความรับผิดชอบของ Domain Service หนึ่งรายการ) เมื่อ Requirement ต้องรองรับ Scenario มากกว่า 5 ตัว หรือครอบคลุม Aggregate Root หลายตัว ควรแยกออกเป็นหลาย Requirement เพื่อป้องกันไม่ให้ AI เสียโฟกัสในการดำเนินงาน

### 2.2 วงจรชีวิตที่ขับเคลื่อนด้วยเวิร์กโฟลว์

เวิร์กโฟลว์ของ OpenSpec สอดคล้องกับการสร้างโมเดลแบบวนซ้ำของ DDD โดยเฉพาะอย่างยิ่งเน้นความสามารถในการ refactor แบบ **Brownfield-first**:

- **Propose (เสนอ) → การสร้างโมเดล domain**: ใช้ `/opsx:propose` เริ่มต้นการเปลี่ยนแปลงอย่างรวดเร็ว และบันทึกผลลัพธ์ของการสร้างโมเดล domain
- **Apply (ดำเนินงาน) → การพัฒนาที่ขับเคลื่อนด้วย Spec**: ใช้ AI ดำเนินการเขียนโค้ดและตรวจสอบอัตโนมัติ (Test to Spec) ตามข้อกำหนด (Requirement + Scenario)
- **Archive (เก็บถาวร) → การรวมความรู้**: ใช้ `openspec archive` รวม Delta Spec เข้าสู่หลัก Spec เพื่อรักษา Single Source of Truth ของความรู้ domain

> **หลีกเลี่ยง Waterfall ขนาดเล็ก**: DDD เน้นการพัฒนาแบบวนซ้ำอย่างต่อเนื่อง และ OpenSpec มีแนวโน้ม "spec ก่อน แล้วค่อยปฏิบัติงาน" อยู่แล้ว เมื่อทั้งสอง.combine กันจะง่ายต่อการหลุดเข้าสู่ Waterfall ขนาดเล็ก แนะนำให้**ก้าวเล็กๆ แต่เร็ว** — รักษาส่วนของ spec และโค้ดให้รวมกันเร็วที่สุดภายใน Changeset เดียว อย่ารอให้โมเดล domain "สมบูรณ์แบบ" ก่อนเข้าสู่ขั้นตอน Apply ทุกรอบของ Archive ให้ถือเป็นการตรึงโมเดลชั่วคราว ไม่ใช่คำตอบสุดท้าย

## 3. กลไกหลัก: การเพิ่มความมั่นใจในการทำงานร่วมกับ AI

OpenSpec ไม่ใช่แค่เอกสาร แต่ใช้ระบบคำสั่งแบบไดนามิกและกลไกการตรวจสอบ เพื่อเพิ่มความมั่นใจในการนำโมเดล DDD ไปใช้งานจริงอย่างมีนัยสำคัญ

### 3.1 ระบบคำสั่งแบบไดนามิกของ AI (OPSX)

OpenSpec 1.0+ แนะนำ OPSX workflow ที่ realized การทำงานร่วมกันผ่าน**การกระทำ ไม่ใช่ขั้นตอน** AI ไม่ได้รับคำสั่งแบบคงที่อีกต่อไป แต่สอบถาม CLI อย่างแข็งขันเพื่อทราบสถานะปัจจุบันของโปรเจกต์ (เช่น ขอบเขต Bounded Context ปัจจุบันและความหมายของ Aggregate ที่มีอยู่แล้ว) เพื่อตัดสินใจที่สอดคล้องกับข้อจำกัดของ domain มากขึ้น

### 3.2 การตรวจสอบที่มีโครงสร้างและการตรวจสอบอัตโนมัติ

OpenSpec ใช้ Schema ที่มีโครงสร้างภายในเพื่อตรวจสอบเอกสาร Spec ทำให้ "spec คือ test" เป็นไปได้จริง:

- **Schema validation**: รับประกันว่า Requirement และ Scenario มีรูปแบบที่ถูกต้อง ป้องกันการแสดงออกที่ไม่เป็นมาตรฐานของ logic domain
- **วงจรตรวจสอบอัตโนมัติ**: AI สร้าง integration test จาก Spec (การจับคู่ Scenario) เพื่อตรวจสอบว่าโค้ดที่เขียนเป็นไปตาม invariant constraint ของ DDD หรือไม่

## 4. แนวทางปฏิบัติที่ดีที่สุด

เพื่อให้ DDD และ OpenSpec ผสานกันได้อย่างมีประสิทธิภาพ แนะนำให้ใช้ "Ubiquitous Language" ตลอดทั้งเวิร์กโฟลว์ และใช้ประโยชน์จากคุณสมบัติการจัดการแบบเพิ่มเติมอย่างเต็มที่

### 4.1 การใช้งาน Ubiquitous Language อย่างต่อเนื่อง

ในการเขียน `proposal.md`, `design.md` และ `spec.md` ต้องใช้ Ubiquitous Language ที่ทีมสร้างขึ้นอย่างเคร่งครัด `config.yaml` ของ OpenSpec ทำให้คำศัพท์เหล่านี้ถูกอ้างอิงอย่างแม่นยำในฐานะ "จุดยึดของบริบท" ในการร้องขอ AI ทุกครั้ง

### 4.2 การตรวจสอบแบบ BDD ที่ขับเคลื่อนด้วย Scenario

ใช้คุณสมบัติที่ Scenario ของ OpenSpec รองรับ Given/When/Then ตามธรรมชาติ เพื่อสร้างเกณฑ์พฤติกรรมที่เข้มงวดสำหรับการออกแบบ Aggregate invariant ทุกตัวที่ระดับ P0 ควรมี Scenario ที่สอดคล้อง เป็นมาตรฐานเดียวสำหรับ AI ในการดำเนินงานและการทดสอบอัตโนมัติ

> **หลักการให้ความสำคัญกับกฎธุรกิจ**: Scenario อธิบายเฉพาะ**กฎธุรกิจและ invariant** เท่านั้น ห้ามใส่รายละเอียดทางเทคนิค (เช่น database operation, HTTP interface, ORM call, cache strategy) รายละเอียดทางเทคนิคให้จัดไว้ใน `design.md` หรือ `tasks.md` ข้อจำกัดนี้สำคัญเท่ากันสำหรับทั้งคนและ AI: การรักษาความบริสุทธิ์ของ domain ใน Scenario เป็นเงื่อนไขที่ทำให้ AI สร้างโค้ดชั้น domain และ test ได้อย่างถูกต้อง

### 4.3 ใช้ประโยชน์จาก Delta และการจัดการการเปลี่ยนแปลงอย่างเต็มที่

OpenSpec อนุญาตให้ทีมพัฒนาคุณสมบัติ domain ที่แตกต่างกันแบบขนานในไดเรกทอรี `changes/` ผ่านกลไก Delta ทีมสามารถโฟกัสเฉพาะ Ability ที่ได้รับผลกระทบจากการเปลี่ยนแปลงปัจจุบัน หลีกเลี่ยงการสูญเสียจุดเน้นเนื่องจากเอกสารที่ซ้ำซ้อนในโปรเจกต์ DDD ขนาดใหญ่

## 5. ตัวอย่างที่ทำงานได้จริงขั้นต่ำ: กรณี "การลงทะเบียนผู้ใช้"

เพื่อช่วยให้ทีมเริ่มต้นได้เร็ว ส่วนนี้ให้ตัวอย่างขนาดเล็ก end-to-end แสดงให้เห็นว่า Ubiquitous Language ถูกใช้งานจาก `proposal.md` ไปถึง `spec.md` ได้อย่างไร สมมติว่า Bounded Context คือ **User Context** ต้องเพิ่มความสามารถ "การลงทะเบียนด้วยอีเมล"

### 5.1 ตัวอย่าง `proposal.md`

```markdown
## Why

ระบบปัจจุบันขาดช่องทางลงทะเบียนผู้ใช้แยกต่างหาก ทำให้ผู้ใช้ใหม่ไม่สามารถสร้างบัญชีได้ด้วยตนเอง

## What Changes

- ภายใต้ User Context เพิ่มความสามารถ: การลงทะเบียนด้วยอีเมล (EmailRegistration)
- เพิ่มเหตุการณ์โดเมน: UserRegistered
- ภาษาที่ใช้ร่วมกัน (Ubiquitous Language): ผู้ลงทะเบียน (Registrant), อีเมล (Email), ลิงก์เปิดใช้งาน (ActivationLink)

## Impact

- Capabilities: user-context/email-registration
- การเปลี่ยนแปลงของ Aggregate: เพิ่ม User Aggregate Root และ invariant ของมัน (ความเป็นเอกลักษณ์ของอีเมล, เครื่องสถานะการเปิดใช้งาน)

## Goals

- อัตราความสำเร็จในการส่งคำขอลงทะเบียน ≥ 99% (ไม่รวมการปฏิเสธทางธุรกิจเนื่องจากอีเมลถูกใช้งานแล้ว)
- อัตราการแปลงจากลงทะเบียน → เปิดใช้งาน ≥ 80%
- เวลาตอบสนองการลงทะเบียนแบบ end-to-end ที่ P95 ≤ 500 ms
```

### 5.2 ตัวอย่าง `specs/user-context/email-registration/spec.md`

```markdown
## Requirement: ความสามารถในการลงทะเบียนด้วยอีเมล

ระบบควรรองรับผู้ลงทะเบียนในการสร้างบัญชีผ่านอีเมล และคงสถานะ Pending ไว้ก่อนการเปิดใช้งาน

### Scenario: ลงทะเบียนสำเร็จด้วยอีเมลที่ยังไม่ถูกใช้งาน

- **Given** Given ระบบไม่มีผู้ใช้ที่มีอีเมล "alice@example.com"
- **When** ผู้ลงทะเบียนส่งอีเมล "alice@example.com" และรหัสผ่านที่ถูกต้อง
- **Then** สร้าง User aggregate ที่มีสถานะเป็น Pending
- **And** เผยแพร่เหตุการณ์ UserRegistered โดยมี UserId และ Email

### Scenario: ปฏิเสธการลงทะเบียนเมื่ออีเมลถูกใช้งานแล้ว

- **Given** ระบบมี User ที่มีอีเมล "alice@example.com" อยู่แล้ว
- **When** ผู้ลงทะเบียนรายอื่นส่งอีเมลเดียวกัน
- **Then** ปฏิเสธการลงทะเบียน และส่งคืนข้อผิดพลาด EmailAlreadyRegistered
- **And** ไม่เผยแพร่เหตุการณ์โดเมนใดๆ
```

> หมายเหตุ: Scenario โฟกัสที่กฎธุรกิจ (email uniqueness, สถานะเริ่มต้นคือ Pending, สำเร็จแล้วต้องเผยแพร่ event) ไม่ได้กล่าวถึง database, HTTP status code, หรือ ORM implementation เนื้อหาเหล่านี้อยู่ใน `design.md` สำหรับการออกแบบทางเทคนิคและ `tasks.md` สำหรับการแยกงาน

## ภาคผนวก A: รูปแบบสำหรับการบรรลุ Event-Driven final consistency

กฎที่ประกาศใน `config.yaml` ว่า "การเปลี่ยนแปลง Aggregate ทั้งหมดต้องผ่าน domain event ขับเคลื่อน final consistency" ต้องมีรูปแบบที่เฉพาะเจาะจงเพื่อให้ AI สร้าง implementation ได้อย่างถูกต้อง ด้านล่างนี้เป็นสองสถานการณ์ที่พบบ่อย

### A.1 เมื่อใดควรเผยแพร่ Event (Publish)

- **ความสอดคล้องข้าม Aggregate**: เมื่อ Command ของผู้ใช้ส่งผลกระทบต่อหลาย Aggregate (เช่น การสั่งซื้อทำให้สินค้าลดลงและยอดเงินในบัญชีเปลี่ยนแปลง) ให้อัปเดตสถานะแบบ synchronous เฉพาะใน**Aggregate ที่ Command ส่งผลกระทบโดยตรง** และเผยแพร่ domain event เพื่อให้ event handler อัปเดต Aggregate อื่นแบบ asynchronous

- **การผสานงานข้าม Context**: เมื่อ Context ภายนอก (เช่น notification, คะแนน, audit) ต้องรับรู้การเปลี่ยนแปลงสถานะของ Context นี้ ให้เผยแพร่ domain event เป็น contract ภายนอก หลีกเลี่ยงไม่ให้ระบบ downstream อ่านสถานะ Aggregate ของ Context นี้โดยตรง

- **เวลาที่เหมาะสม**: Event ควรเผยแพร่**หลังจากบันทึกลง database ของ Aggregate แล้ว** ในขณะที่ทำ transaction commit (แนะนำใช้ Outbox pattern) เพื่อรักษาความสอดคล้องระหว่าง event กับการเปลี่ยนแปลงสถานะ

### A.2 วิธีบริโภค Event (Consume)

- **การบริโภคแบบ Idempotent**: Event handler ต้องมี idempotent key (โดยปกติคือ `AggregateId + Version` หรือ `EventId`) เพื่อป้องกันไม่ให้การส่งซ้ำทำให้สถานะ Aggregate ผันผวน

- **กลยุทธ์เมื่อล้มเหลว**: เมื่อบริโภคล้มเหลว ควรเข้าสู่ retry queue หรือ dead letter queue ห้าม rollback Aggregate ฝั่งต้นน้ำ การชดเชยข้าม Aggregate ทำได้ผ่านการเผยแพร่ compensating event (เช่น `OrderCancelled`)

- **การแปลงระหว่าง Context**: เมื่อบริโภค event ข้าม Context ต้องผ่าน Anti-Corruption Layer (ACL) เพื่อแปลง semantics จากฝั่งต้นน้ำเป็น Ubiquitous Language ของ Context นี้ หลีกเลี่ยงไม่ให้โมเดลจากฝั่งต้นน้ำรั่วไหลเข้ามา

### A.3 ตัวอย่าง Event Chain สำหรับการสั่งซื้อ

> ใน event chain นี้ แต่ละ Aggregate รับผิดชอบเฉพาะสถานะภายในของตนเท่านั้น ความสอดคล้องข้าม Aggregate ทำได้ผ่าน event และ compensating action เมื่อ AI ดำเนินการ flow ลักษณะนี้ ควรปฏิบัติตาม constraint "ธุรกรรมหนึ่งแก้ไข Aggregate เดียว" อย่างเคร่งครัด
