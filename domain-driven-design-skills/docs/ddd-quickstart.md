# DDD Skill คู่มือเริ่มต้นอย่างรวดเร็ว（Quickstart）

> 🌐 English version: [English](ddd-quickstart.en.md)

---

> บทความนี้ตอบคำถามสามข้อ: Skill ชุดนี้คืออะไร? รันที่ไหน? จะเริ่มจากศูนย์จนถึงการสร้าง Domain Model ได้อย่างไร?
> ผู้อ่านเป้าหมาย: นักพัฒนาที่เพิ่งมาสัมผัส repository นี้เป็นครั้งแรกและต้องการลองใช้งานทันที

## 1. Skill ชุดนี้คืออะไร?

- **ไม่ใช่ซอฟต์แวร์ที่ติดตั้งได้** แต่เป็น**ชุดคำสั่ง**สำหรับ AI Assistant (สภาพแวดล้อมสนทนาที่รองรับ Agent Skill)
- Skill แต่ละตัวคือไฟล์ `SKILL.md`: บอก AI ว่าในขั้นตอนการสร้างโมเดลแต่ละจุด "ต้องทำตามกระบวนการอะไร ผลิต Artifact รูปแบบใด"
- Skill 9 ตัวประกอบกันเป็น **ขั้นตอน 5 ระยะ**: การจำกัดขอบเขต（I）→ การออกแบบเชิงกลยุทธ์（II）→ การออกแบบเชิงยุทธวิธี（III）→ การตรวจสอบโมเดล（IV）→ การเชื่อมต่อ OpenSpec（V）Artifact ของแต่ละระยะจะเป็น Input ของระยะถัดไป

## 2. สิ่งที่ต้องเตรียมก่อน

| ต้องการ                        | คำอธิบาย                                                          |
| :------------------------------ | :---------------------------------------------------------------- |
| เครื่องมือ AI ที่รองรับ Agent Skill | เช่น Claude Code, Qoder หรือสภาพแวดล้อมที่รองรับ `@skill` syntax หรือ Skill Directory |
| Git                         | สำหรับ Clone repository นี้                                    |
| Runtime Environment                    | **ไม่มี**——repository นี้เป็น pure documentation/spec repository ไม่ต้องติดตั้ง dependencies หรือเริ่ม Services                    |

Clone repository:

```sh
git clone --recurse-submodules https://github.com/ForceInjection/domain-driven-design-skills.git
```

วิธีนำ Skill มาใช้ (เลือก 1 ใน 2):

- **วิธี A (แนะนำ)**: คัดลอกโฟลเดอร์ `skills/ddd-*/` ไปที่ Skill Directory ของเครื่องมือ AI ของคุณ (เช่น `~/.claude/skills/` ของ Claude Code หรือ `.claude/skills/` ของ Project) จากนั้นเรียกใช้ได้ทันทีด้วย `@ddd-*`
- **วิธี B**: ไม่ต้องคัดลอก ให้คัดลอกเนื้อหาของ `skills/<skill>/SKILL.md` ไปวางเป็นคำสั่งใน Session ของ AI โดยตรง แล้วใส่คำอธิบายธุรกิจเป็น Input

## 3. ก่อนเริ่มงาน: การสัมภาษณ์และการจัดระเบียบความต้องการ（ขั้นตอนสำคัญ）

Input ของ `@ddd-scope` คือ**คำอธิบายธุรกิจ** ซึ่งคำอธิบายธุรกิจไม่ได้เกิดขึ้นมาลอยๆ——มันมาจาก**การสัมภาษณ์**และ**การจัดระเบียบความต้องการ**จากฝั่งธุรกิจ คุณภาพของโมเดลขึ้นอยู่กับความเข้าใจธุรกิจของคุณ ดังนั้นนี่จึงเป็นขั้นตอนสำคัญก่อนเริ่มใช้ Skills

### 3.1 สัมภาษณ์ใคร

| ผู้ถูกสัมภาษณ์                           | สามารถให้ข้อมูลอะไรได้บ้าง                             |
| :--------------------------------- | :------------------------------------- |
| ฝั่งธุรกิจ (Domain Expert)                 | เป้าหมายทางธุรกิจ ภาพรวมของกระบวนการ กฎเกณฑ์และข้อยกเว้น         |
| ผู้ปฏิบัติงานจริง (ฝ่ายบริการลูกค้า / การรับประกันภัย / การเรียกร้อง เป็นต้น) | วิธีทำงานจริง สถานการณ์ที่อาจเกิดข้อผิดพลาด Pain Points ของระบบ |
| ฝ่ายบริหาร                             | เป้าหมายและข้อจำกัด (กฎระเบียบ งบประมาณ ไทม์ไลน์)         |
| ผู้รับผิดชอบระบบ (ถ้ามีระบบที่ใช้อยู่)         | ขอบเขตของระบบเดิม แหล่งที่มาของข้อมูล                 |

### 3.2 ถามอะไร (Interview Outline)

- **เป้าหมายทางธุรกิจ**: ต้องการแก้ปัญหาอะไร? ตัวชี้วัดความสำเร็จคืออะไร?
- **กระบวนการหลัก**: งานหนึ่งตั้งแต่เริ่มจนจบเป็นอย่างไร? (ให้ฝั่งธุรกิจเล่าให้ฟังครบถ้วน)
- **บทบาท**: ใครเกี่ยวข้องบ้าง? แต่ละคนทำอะไร?
- **ข้อผิดพลาดและข้อยกเว้น**: สถานการณ์ใดที่อาจเกิดปัญหา? เมื่อเกิดปัญหาแล้วจัดการอย่างไร?
- **คำศัพท์เฉพาะ**: เรียกสิ่งต่างๆ เหล่านี้ว่าอะไร? (บันทึกคำพูดของฝั่งธุรกิจ——คำเหล่านี้อาจเป็น seed ของ Ubiquitous Language สำหรับการสร้างโมเดล)

### 3.3 จัดระเบียบเป็นคำอธิบายธุรกิจอย่างไร

บันทึกการสัมภาษณ์ → การจัดระเบียบความต้องการ → คำอธิบายธุรกิจ:

1. เป้าหมายและ non-goal (ทำอะไร / ไม่ทำอะไรชัดเจน)
2. กระบวนการหลัก + สถานการณ์ผิดพลาด (คิดให้ชัดอย่างน้อย 2–3 สถานการณ์ที่อาจเกิดปัญหา)
3. รายชื่อบทบาท
4. ตารางคำศัพท์เฉพาะของฝั่งธุรกิจ (คำพูดเดิม)
5. ข้อจำกัดและความเสี่ยง

จัดเป็นคำอธิบายปัญหา 3–5 ประโยค (Pain Point ปัจจุบัน + เป้าหมายที่ต้องการ) นั่นคือ Input สำหรับ `@ddd-scope`

> ถ้าคุณเป็นฝั่งธุรกิจเอง: ให้เล่าด้วยคำของคุณเองให้ AI ฟังได้เลย ข้ามขั้นตอนการสัมภาษณ์ไปได้

## 4. บทสนทนาแรก: `@ddd-scope`

ให้ AI รับคำอธิบายธุรกิจที่คุณจัดระเบียบแล้ว (จากขั้นตอนที่ 3 ซึ่งอาจยังคลุมเครือและไม่เป็นโครงสร้างได้):

AI จะผลิต Artifact ที่มีโครงสร้าง: Problem Statement และ Value Statement, เป้าหมาย/non-goal, ตารางข้อจำกัดและสมมติฐาน, รายชื่อคำศัพท์เฉพาะ (≥10 คำ), รายการความเสี่ยง

## 5. การส่งต่อ Artifact: `@ddd-discover` → … → `@ddd-model-review`

คัดลอก Output ของ Skill ที่แล้วไปใส่ให้ Skill ถัดไป:

เดินให้ครบทั้ง 8 Skill สำหรับการสร้างโมเดล（ระยะ I–IV）**ไม่จำเป็นต้องทำให้ครบทุกครั้ง**: สามารถเข้าได้จากทุกระยะ (Project ใหม่ / ระบบที่มีอยู่ / เฉพาะจุด / ตรวจสอบโมเดล ดูได้ที่ [README](../README.md) ในส่วนตารางทางเข้า) สามารถหยุดชั่วคราวได้ตลอดเวลาแล้วกลับมาทำต่อโดยใช้ Artifact ที่มีอยู่แล้วในครั้งถัดไป

## 6. เมื่อทำเสร็จแล้วคุณจะได้อะไร?

เมื่อเดินครบทุกขั้นตอน คุณจะมี**Artifact ที่มีโครงสร้างครบชุด**:

| ระยะ     | ตัวอย่าง Output                                                                                            |
| :------- | :-------------------------------------------------------------------------------------------------- |
| I Discovery   | Problem Statement, ตาราง Event Flow (เส้นทางหลัก + สาขาผิดพลาด), คำศัพท์เฉพาะ                                                   |
| II Strategic  | การจัดประเภท Subdomain (Core/Supporting/Generic), รายชื่อ Bounded Context, ตาราง Ubiquitous Language, Boundary ADR, Context Map และ Integration Patterns |
| III Tactical | รายชื่อ Aggregate และตาราง Invariant, รายการ Entity/Value Object, รายชื่อ Domain Event, Domain Service, Repository Interface, Factory |
| IV Validation  | การให้คะแนนตามมิติ, รายการปัญหา, การตัดสินย้อนกลับ (Ready / Not Ready)                                                 |

ต้องการดูผลงานจริงที่สมบูรณ์? ใน `validation-cases/` มี 2 กรณีตัวอย่างแบบ End-to-End:

- [cargo-validation](../validation-cases/cargo-validation/): สาขาโลจิสติกส์ มี Reference Implementation สำหรับเทียบเคียง (คะแนน 85.8%) มี Artifact ครบทั้ง 01–08
- [insurance-validation](../validation-cases/insurance-validation/): การรับประกันภัยและการเรียกร้อง ไม่มี Reference Implementation (ผู้เชี่ยวชาญให้คะแนน 90.9%) มี Artifact ครบทั้ง 01–09 (09 คือ OpenSpec Change Set)

## 7. การเชื่อมต่อกับการพัฒนาจริง: `@ddd-openspec-bridge`（ระยะ V）

ผลลัพธ์จากการสร้างโมเดลจะถูกแปลงเป็น Engineering Specification ที่สามารถนำไปใช้ได้จริงในระยะ V:

เมื่อได้ OpenSpec Specification (Requirement + Scenario ในรูปแบบ Gherkin) แล้ว ส่งต่อให้นักพัฒนาหรือเครื่องมือ AI ถัดไปเพื่อ implement โค้ดตาม Spec——**repository นี้ไม่ได้สร้าง Business Code**, การสร้างโมเดลและการเชื่อมต่อ Spec คือขอบเขตของมัน

### 8. FAQ

| คำถาม                          | คำตอบ                                                                                          |
| :---------------------------- | :-------------------------------------------------------------------------------------------- |
| Skill รันที่ไหน?            | ในสภาพแวดล้อม AI Assistant ไม่ใช่ Program อิสระ; เรียกใช้ด้วย `@skill-name` syntax                                     |
| ต้องเขียนโค้ดไหม?                | ไม่ต้อง Repository นี้มุ่งเน้น Domain Modeling และการเชื่อมต่อ Spec (OpenSpec) การ implement โค้ดทำโดยนักพัฒนาหรือ AI ถัดไป              |
| Output เป็นตารางเยอะๆ มีประโยชน์อะไร?      | เป็น Input ของ Skill ถัดไป (รับประกันว่า Artifact สามารถเชื่อมต่อกันได้) และเป็นที่มาของ OpenSpec Specification                         |
| ข้ามบางขั้นตอนได้ไหม?            | ได้ ดูที่ [README](../README.md) "ทางเข้าและวิธีเรียกใช้" เลือกทางเข้าตาม Scenario                            |
| ข้อกำหนด Output ของแต่ละ Skill คืออะไร? | `SKILL.md` ของแต่ละ Skill มีตาราง Output, รายการตรวจสอบ และเงื่อนไขการย้อนกลับ, AI จะปฏิบัติตาม                            |
| คุณภาพของโมเดลจะรับประกันอย่างไร?            | ระยะ IV `ddd-model-review` ให้คะแนนตามมิติและย้อนกลับถ้าจำเป็น (เช่น อัตราการแสดง Invariant ต่ำกว่า 60% จะย้อนกลับไปที่ `ddd-aggregates`) |
| ดูตัวอย่างที่สมบูรณ์ได้ที่ไหน?              | Artifact 01–09 ของ 2 กรณีใน `validation-cases/` คือ Walkthrough ที่สมบูรณ์                                           |
